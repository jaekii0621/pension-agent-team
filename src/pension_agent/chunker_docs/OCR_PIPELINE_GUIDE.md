# OCR 파이프라인 사용 가이드

**대상**: doc57(검증완료), doc58(검증완료, 재검증완료), doc33(검증완료), doc53(검증완료), doc22(검증완료) → 남은 이미지PDF 18개에 재사용
**코드**: `ocr_pdf.py`(요청 담당) + `build_chunk_from_ocr.py`(응답→Chunk 변환 담당)

---

## 1. 전체 흐름

```
원본 PDF (data/raw/docXX.pdf)
        ↓  ocr_pdf.py 실행
docXX_ocr_response.json (OCR 원본 응답, 중간 재료)
        ↓  build_chunk_from_ocr.py 실행
chunks_docXX_ocr.jsonl (최종 청크 결과물)
```

**두 스크립트 다 이미 완성돼서 재사용 가능한 상태.** 문서마다 코드를 새로 짤 필요 없이, 파일명이랑 문서ID만 바꿔서 실행하면 됨.

**pptx(doc33 등)는 예외**: CLOVA OCR이 pptx를 직접 못 받으므로, 파워포인트에서 "다른 이름으로 저장 → PDF"로 먼저 변환한 뒤 위 흐름 그대로 적용.

**결과물 저장 위치**: `chunks_docXX_ocr.jsonl`은 최종적으로 **`data/chunks/`**에 저장. `chunker_docs/`는 코드 파일 전용 폴더이고, 결과물을 여기 남겨두면 안 됨 (doc22 작업 때 한 번 잘못 올렸다가 옮긴 적 있음).

## 2. 문서 하나 처리하는 표준 절차

### Step 1 — 페이지 범위 확인
`ocr_pdf.py`에서 `pdf_path`, `PAGE_NUMBERS`, `OUTPUT_PATH` 3곳을 대상 문서에 맞게 수정. 전체 페이지가 필요하면 `PAGE_NUMBERS = None`, 특정 페이지만 필요하면 리스트로 지정(예: `[3, 5]`).

⚠️ **`OUTPUT_PATH`를 매번 손으로 안 바꾸면, 이전 문서 처리 때 만든 파일을 덮어써버림** (doc22 처리 때 doc53 결과 파일이 그대로 덮어써진 적 있었음). 문서 바꿀 때마다 이 줄 꼭 확인할 것.

### Step 2 — OCR 요청 실행
```powershell
python ocr_pdf.py data/raw/docXX.pdf
```
→ `docXX_ocr_response.json` 생성됨.

### Step 3 — Chunk로 변환
```powershell
python build_chunk_from_ocr.py docXX_ocr_response.json docXX
```
→ `chunks_docXX_ocr.jsonl` 생성됨. 이게 최종 결과물.

**source 값도 매번 확인**: `build_chunk_from_ocr.py` 맨 아래 `__main__`의 `source="..."` 인자가 문서 내용에 맞는 값인지 확인. 한 문서 안에서도 페이지별로 성격이 다를 수 있음(예: doc22는 절차 설명 페이지와 세제/과세 설명 페이지가 섞여있었음 → 아래 5-2 참고).

### Step 4 — 육안 확인 (필수)
터미널 출력은 150자로 잘려 보이므로, **반드시 jsonl 파일을 직접 열어서 전체 텍스트를 원본 PDF/이미지와 대조**할 것. 특히:
- 숫자/퍼센트/조문 번호가 그대로인지
- 문장이 중간에 뚝 끊긴 곳은 없는지
- **페이지가 표/문단이 아니라 박스형 다이어그램(플로우차트, 조직도)인지** — 이 경우 자동 청크가 여러 박스 내용을 한 문장으로 뭉쳐버릴 수 있음 → 아래 5-1 참고

## 3. doc57 → doc58 → doc33 진행하며 잡은 버그 (다음 문서에도 똑같이 적용됨)

| # | 이슈 | 원인 | 해결 |
|---|---|---|---|
| 1 | 워터마크(`129/2026-02-25` 등)가 표 안에 섞임 | 대각선 워터마크 도장이 표 영역과 좌표상 겹침 | 글자 박스가 "회전"되어 있으면(직사각형이 아니면) 걸러냄 |
| 2 | 병합된 분류("채무증권" 등)가 첫 행에만 나오고 나머지 행은 빈칸 | `rowSpan`을 안 펼치고 그리드에 반영 안 함 | `rowSpan`/`columnSpan`만큼 값을 반복해서 채우도록 수정 |
| 3 | "운용방법: X, 운용방법: X, 운용방법: X" 3번 중복 | 헤더도 병합돼서 같은 헤더가 여러 열에 복제, 값도 같이 복제되며 짝지어짐 | 한 행 안에서 완전히 똑같은 (헤더,값) 짝은 한 번만 남기게 수정 |
| 4 | ⚠️ **`100분의 40`에서 `40`이 통째로 사라짐** | "외로운 짧은 숫자=노이즈"로 판단하는 필터를 표 안에도 적용해서, 진짜 퍼센트 수치까지 삭제됨 | 표 안에서는 회전 필터만 쓰고, 외로운 숫자 필터는 표 밖 본문에만 적용하도록 분리 |
| 5 | ⚠️⚠️ **doc33에서 세액공제 관련 핵심 문장 한 줄이 통째로 사라짐** | 표의 "바깥 경계 큰 사각형" 기준으로 "표 영역이니 제외" 판단을 해서, 표 밖인데 그 큰 사각형 안에 걸쳐있던 진짜 본문 문장이 본문에도 표에도 안 들어가는 사각지대에 빠짐 | 표 전체의 큰 경계 대신, **실제 셀 하나하나의 좁은 경계**로 판단하도록 수정 |
| 6 | ⚠️⚠️⚠️ **(5번을 고쳤는데도 안 고쳐졌던 진짜 원인)** 정상 글자가 워터마크로 오인되어 삭제됨 (예: "전환완료") | 회전 판단 로직이 **오차를 전혀 허용 안 해서**, OCR이 1~2픽셀 정도 어긋나게 인식한 정상 글자까지 "회전됐다"고 오판함 | 회전 판단에 **오차 허용 범위(tolerance, 기본 8픽셀)**를 추가. 진짜 워터마크(수십 픽셀 이상 차이)는 여전히 잘 걸러지고, 정상 글자의 미세한 오차는 통과되도록 수정 |
| 7 | 자잘한 페이지번호("46") 잔재 | 원본이 더 큰 문서(152p)에서 일부만 뽑혀서, 원래 있던 페이지 번호가 표 경계와 겹쳐 완전히 안 걸러짐 | 완벽 자동 제거 안 됨 — **청킹 단계에서 손으로 정리하기로 함** (심각한 문제 아님, 내용 왜곡 없이 끝에 숫자만 붙는 정도, 아직 미해결) |
| 8 | ⚠️⚠️ **doc22에서 박스형 다이어그램 페이지(연금 수령방식, 과세구분)의 서로 다른 박스 내용이 한 문장으로 뭉쳐짐** | 이 페이지엔 애초에 `tables` 키가 없음(표가 아니라 플로우차트라서 CLOVA가 표로 인식 못 함) → `fields`만 좌표 순서대로 나열되는데, 박스 구조 정보가 없어서 인접한 다른 박스 내용이 섞여 이어붙음 | **코드로 해결 불가능한 유형** — 원본 이미지 보고 박스 단위로 손으로 재분할. 새 문서 처리 시 "표/문단"이 아니라 "박스+화살표 다이어그램" 페이지가 있으면 자동 청크를 그대로 믿지 말고 수작업 전제로 접근할 것 |

**핵심 교훈 3가지**:
1. 노이즈 필터는 "표 안"과 "표 밖"을 다르게 취급해야 함. 표 안의 짧은 숫자는 대부분 진짜 데이터(퍼센트/한도 등)일 가능성이 높음.
2. **"이상한 게 안 보인다"가 "정상이다"를 보장하지 않음.** 5번·6번 버그는 둘 다 코드가 에러 없이 조용히 돌아갔고, 터미널 출력만 봐서는 전혀 이상해 보이지 않았음. 오직 **원본 이미지와 한 문장씩 대조**해서만 발견됨. → 새 문서 처리할 때마다 Step 4(육안 확인)를 생략하면 안 됨.
3. **표 vs 박스형 다이어그램은 근본적으로 다른 문제.** 표는 `rowIndex`/`columnIndex`라는 구조 정보가 있어서 코드로 재구성 가능하지만, 플로우차트/조직도는 그런 정보가 아예 없어서 좌표 순서만으로는 원래 구조를 복원할 수 없음. 이런 페이지는 "버그를 고친다"가 아니라 "애초에 자동화 대상이 아니다"로 접근해야 함.

**⚠️ 재검증 필요**: 6번 버그(회전 tolerance)는 doc57에서는 영향이 없었을 가능성이 높지만(표가 단순해서), 아직 doc57로 명시적으로 재확인은 안 함. 여유 될 때 `doc57_ocr_response.json`으로 최신 코드 재실행해서 결과 달라지는지 확인 권장.

## 5. 참고 — doc22 처리 중 새로 생긴 패턴

### 5-1. 박스형 다이어그램 페이지 처리법
1. Step 4 육안 확인 시, 자동 생성된 청크 하나에 서로 다른 항목(예: "정기연금" 설명과 "비정기연금" 설명)이 섞여 있으면 이 유형으로 의심
2. 원본 이미지에서 박스 경계를 눈으로 확인하고, 박스 하나 = 청크 하나로 재작성
3. **원문 단어·구절은 그대로 유지**하고 순서만 박스 단위로 재배열(문장으로 매끄럽게 다시 쓰지 않음) — 다른 문서들과 스타일 통일 위해, 그리고 세제/법령 내용은 표현을 바꾸면 뉘앙스가 달라질 위험이 있어서
4. section 필드는 해당 박스의 제목으로 지정

### 5-2. 페이지별 source가 다른 경우
한 문서 안에서도 페이지 성격이 다르면(예: 절차 설명 페이지 vs 세제/과세 설명 페이지), `build_chunk_from_ocr.py`가 문서 전체에 source 하나만 적용하는 구조라 자동으로는 처리 안 됨.
→ **1차로 전체에 기본 source 적용해서 생성 → 이후 해당 페이지만 골라 source 값 스크립트로 일괄 수정** (간단한 파이썬 스크립트로 jsonl 읽어서 `page` 기준으로 `source` 덮어쓰기)
