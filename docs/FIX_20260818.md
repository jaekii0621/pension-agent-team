## 5. 검색이 카드로 쏠림 (요청 3·4번) — **card_boost 는 곱셈입니다**

### 요청 내용
> 정규화 코사인 점수에 0.5를 더하면 카드가 거의 항상 이깁니다.

### 실제 코드
```python
# index/store.py:238
m = 1.0 + config.CARD_BOOST * affinity     # 0.5 × 0.35 → ×1.175
w *= m
```
**더하기가 아니라 곱하기**입니다. 관여도 0.35면 ×1.175, 0.85여도 ×1.425.
이게 중요한 이유는 아래 §8 에서 드러납니다.

### 원인은 3단으로 겹쳐 있었습니다

**1단 — 펀드명 추출 실패 (진짜 시작점)**

P-F4/G0a/G0b 모두 질문에 "미래에셋장기성장포커스"가 있는데 `product_affinity` 가
기본값 0.35 였습니다. `query_analyzer` 가 펀드명 추출을 **LLM 에게만** 맡겼는데
HCX-DASH-002 가 세 문항 모두 놓쳤습니다.

**2단 — tier 쿼터**: 관여도 0.35 → `q_pros = round(8 × 0.35) = 3`.
투자설명서 7,339건이 3칸을 놓고 경쟁 → 섹션에 도달 불가.

**3단 — 카드/섹션 쿼터 부재**: `MIN_STRATUM_QUOTA` 는 doc↔prospectus 사이만 조정.

### 수정 — 1단을 고치는 게 핵심이었습니다

`safety_checker` 에 이미 있던 목록 대조 함수를 `index/loader.py` 로 올려
`query_analyzer` 도 쓰게 했습니다. **LLM 이 놓치면 목록 대조가 받칩니다.**

```python
if not clean["fund_name"]:
    hit = match_known_fund(question)      # 문자열 비교. 오탐 0, LLM 0회
    if hit:
        clean["fund_name"] = [hit]        # → affinity 0.35 → 0.85
```

**실제 코퍼스 검증 결과** (7,939건, BM25 단독):

| 문항 | 펀드명 검출 | 관여도 | 섹션 확보 (수정 전 → 후) |
|---|---|---|---|
| P-F4 | ✅ | 0.35 → 0.85 | 3/8 → **6/8** |
| P-G0a | ✅ | 0.35 → 0.85 | 3/8 → **6/8** (관련회사 섹션 진입) |
| P-G0b | ✅ | 0.35 → 0.85 | 3/8 → **6/8** (관련회사 섹션 진입) |
| P-E4 | ✅ | 0.35 → 0.85 | 2/8 → **5/8** |

P-G0a/G0b 가 필요로 하던 **「관련회사」 섹션이 실제로 올라왔습니다.**

```
· 제시하되 단정하지 않는다. …
```

"금지"를 앞세우던 것을 "**의무 → 그 다음 제약**" 순서로 뒤집었습니다.
진단하신 대로 **위치가 safety 노드가 아니라 답변 프롬프트**였습니다.

## 8. ⚠️ 섹션 쿼터 — 요청과 다르게 나간 유일한 항목

### 제가 처음에 드린 판단
> card_boost 를 0.1 로 낮춰도 카드가 여전히 3자리를 다 먹습니다.
> **chunk_type 단위 최소석 보장이 필요합니다.**

### 실측 결과 — 그 판단이 틀렸습니다

실제 코퍼스로 ablation 을 돌렸습니다
(`scratchpad/ablation.py`, 7,939건, top_k=8, affinity=0.85):

| 설정 | 섹션 질문의 섹션 확보 | 카드 질문의 카드 확보 |
|---|---|---|
| **수정 전** boost .50 / 쿼터 0 | 16 | 11 |
| boost .25 / 쿼터 0 | **23** | 10 |
| boost .25 / 쿼터 1 | 23 | 9 |
| boost .25 / 쿼터 2 | 23 | **8** |

읽는 법:

- 섹션 개선(16 → 23)은 **전부 `CARD_BOOST` 인하가 만들었습니다.**
- **쿼터는 섹션을 하나도 더 늘리지 못했습니다** (23 → 23 → 23).
  자연 순위가 이미 쿼터보다 많은 섹션을 뽑고 있어서 바닥값이 걸리지 않습니다.
- 반대로 카드가 정본인 질문에서는 쿼터가 걸려 카드를 밀어냈습니다
  (C3 "C-P 클래스 가입자격": 6장 → 5장 → 4장).

**즉 지금 데이터에서 쿼터는 이득 0 / 비용 있음입니다.**

### 그래서 어떻게 했나

기제(`_take_prospectus`)는 넣되 **기본값을 0(비활성)** 으로 뒀습니다.

**코드를 남긴 이유**: 위 측정은 **벡터 아티팩트가 없어 BM25 단독**으로 돌렸습니다.
원래 문제를 만든 실측(카드 46.1% / 섹션 8.6%)은 **벡터가 켜진** 실행입니다.
카드는 짧고 의미가 응축돼 코사인에서 훨씬 유리하므로, 벡터를 켜면
카드가 다시 섹션을 밀어낼 수 있습니다. 그때는 바닥값이 필요합니다.

**재측정 방법**:
```bash
python -m index.build_index
python scratchpad/ablation.py
```
"쿼터 0" 의 섹션 확보가 다시 떨어지면 `PENSION_MIN_SECTION_QUOTA=2` 로 켜면 됩니다
(코드 수정 불필요).

## 9. LLM 예산 (요청 비용 문단)

### 왜 안 걸렸나
`LLM_CALL_BUDGET=40` 을 보는 코드가 **한 곳뿐**이었습니다.

```python
# edges/decomposition.py — should_repeat() 안, "라운드를 한 번 더 돌까?" 시점
if (state.get("llm_calls", 0) or 0) >= config.LLM_CALL_BUDGET:
```

호출을 실제로 태우는 곳은 서브질문 fan-out **안쪽**의 재검색·재작성·재생성
루프인데, 그 루프는 예산을 전혀 안 봤습니다. **한 라운드를 다 태운 뒤에야**
"예산 소진" 판정이 납니다. 그래서 예산 40에 실측 최대 95회.

### 수정 — 3중 게이트

| 층 | 위치 | 동작 |
|---|---|---|
| ① 호출 카운터 | `llm.calls_for_question()` | 질문당 호출 수 실시간 집계 |
| ② 소프트 제동 | `edges/retrieval_check.py`, `edges/verification_check.py` | `over_budget()` 이면 재시도 포기 → `give_up` (답변은 나온다) |
| ③ 하드 상한 | `llm._post()` 진입부 | `LLM_CALL_HARD_CAP=60` 초과 시 `LLMBudgetExceeded` |
| ④ 2차 방어선 | `edges/decomposition.py` | 기존 라운드 경계 검사 유지 |

②가 핵심입니다. **호출이 생기는 지점에서 끊어야** 실제로 줄어듭니다.

지연은 리포트에 p50/p90/max 를 찍게 했습니다 — 평균은 타임아웃을 숨깁니다
(실측 중앙 45초 / 최대 114초).

## 10. 산출물 필드 (요청 12번 체크리스트)

### `COMPACT_KEYS` (⚠️ 요청서의 `COMPACT_FIELDS` 는 실제 이름이 다릅니다)

```python
COMPACT_KEYS = [
    ...,
    # --- 안전 판정 (정당한 거절 vs 오차단 구분에 필수) ---
    "blocked", "safety_reason", "safety_category", "safety_caution",
    # --- 근거 (검색 실패인지 인용 실패인지 갈리려면 둘 다 필요) ---
    "n_citations", "cite_dist", "retrieval_dist", "dangling_cites",
    "citations", "retrieval",
    # --- 계산 (산술 오류의 원인이 도구인지 LLM 암산인지) ---
    "calc",
    ...
]
```

### `retrieval_dist` — 검색 실패와 인용 실패를 가른다

`cite_dist`(인용된 것)와 **짝을 이룹니다**:

| 상황 | 판정 | 고칠 곳 |
|---|---|---|
| 검색 분포에 원하는 타입이 없다 | 검색 실패 | 쿼터·가중·필터 |
| 검색엔 있는데 인용엔 없다 | 인용 실패 | 답변 프롬프트 |

`document_retriever` 가 `trace.detail["chunk_type_dist"]` 에 **dict 로** 남깁니다
(예전에는 summary 문자열 안에만 있어서 정규식으로 다시 파싱해야 했습니다).

### `calc` — 도구를 탔는지 LLM 이 암산했는지

```json
{"tool_name": "tax_credit_limit", "used_tool": true,
 "args": {"salary": 60000000}, "numbers": {"limit": 6000000}}
```
`used_tool: false` 면 LLM 이 직접 계산한 것이고, 그러면 틀리는 게 당연합니다.
고칠 곳은 계산기가 아니라 **도구 선택 프롬프트**(`calculator_select_system`)입니다.

## 11. 채점 (요청 10·11·13·14번)

### 축별 점수 — `metrics.axis_scores()`

```python
{
  "auto":  {"retrieval": 0.75, "retrieval_doc": …, "grounding": 1.0},  # 자동, 채움
  "human": {"usefulness": None, "safety": None},                       # 사람, 빈칸
  "gate":  {"blocked": True, "category": "개인정보", "caution": "", "clarified": False},
}
```

**사람 2축을 `None` 으로 비워 두는 것이 중요합니다.** LLM 심판 점수를 사람 점수
자리에 넣으면 "사람이 확인했다"와 "모델이 추측했다"가 구분되지 않습니다.

`gate` 는 점수가 아니라 **사실 기록**입니다. 정당한 거절(개인정보)과 오차단
(위법조력 오판)은 같은 '차단'이지만 채점이 정반대여야 하므로, 범주를 그대로
남기고 판정은 채점자에게 맡깁니다.

### `gold_ids_for()` — 골드셋 두 모양 모두 수용

```python
{"gold_chunk_ids": ["doc57-p3-s2"]}                    # ① 기존
{"evidence": [{"chunk_id": "doc57-p3-s2", "quote": …}]} # ② 인용 단위로 적을 때
```
예전에는 ①만 봐서, ②로 적으면 `retrieval_metrics` 가 **빈 dict 를 반환**했습니다
(= 검색 지표가 통째로 사라짐).

### `retrieval_metrics_doc()` — 청크 정답의 잡음 제거

같은 내용이 인접 두 청크에 걸쳐 있으면 어느 쪽을 정답으로 적어도 맞는데,
chunk_id 하나만 적으면 다른 쪽을 가져온 실행이 **틀린 것으로 채점**됩니다.

- 청크 recall 낮음 + 문서 recall 높음 → 청킹/랭킹 미세 문제
- 둘 다 낮음 → 진짜 검색 실패

### 새 CLI

```bash
python -m eval.run_queryset --split dev        # 튜닝용만
python -m eval.runner --split holdout          # 최종 확인용만
python -m eval.runner --from-compact eval/results/xxx.compact.jsonl   # LLM 0회 재채점
```

`--from-compact` 는 78문항 260만 토큰을 다시 태우지 않고 **채점 규칙만 바꿔서**
결정론적 지표를 다시 계산합니다.
