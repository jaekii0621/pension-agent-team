## 1. P-E5 는 절반이 아니라 세 군데가 틀려 있었다

9차 검토서는 "표 제목이 뒤바뀜"으로 적었는데, 원자료를 다시 맞춰 보면 셋이다.

| | 답변 | 자료 |
|---|---|---|
| **① 표 합성** | 첫 표의 제목·열라벨은 p47 「나. 연도별 수익률 추이」(최근1년차~5년차) | 값은 p46 「가. 연평균수익률」 행 그대로 |
| **② 행 혼합** | 종류C4: `-23.62 · 1.79 · -10.60` \| `18.96 · 33.33` | 앞 셋은 p46, 뒤 둘은 p47 |

10차는 마크다운 표. **차수와 형태가 바뀌어도 같은 칸에서 같은 실패가 난다.**

### 1-3. 새 가드 — 값이 다 맞아도 잡는다

`unsupported_values` 는 집합 대조라 "이 값이 **어딘가에** 있는가"만 본다. ①②③ 셋 다
값 자체는 자료에 있으므로 원리상 통과한다. 그래서 **순서와 축**을 본다.

```
① 행 혼합    행의 값들이 어느 한 청크에도 연속으로 들어 있지 않다 (역순은 인정)
② 축 불일치  값이 나온 청크에 답변이 붙인 열 이름이 없다
③ 목록형     굵은 소제목 밑 계열의 끝 한 칸만 다른 표에서 온 경우
```

역순을 인정하는 이유: 답변이 열 순서를 뒤집어 제시하는 것은 오류가 아니다.
10차 둘째 표는 원문이 24년→20년인데 답변은 20년→24년으로 썼고 그건 정상이다.

|---|---|---|

## 2. 지표가 답변의 표기 습관을 따라다니고 있었다

### 2-1. 기간 라벨이 인용을 붙이고 있었다

10차 P-E5 의 인용 3건은 quote 가 전부 이랬다.

```
[1] p47  값 일치: 1년, 2년, 3년, 4년
[2] p48  값 일치: 1년, 2년, 3년, 4년      ← 「자산구성 현황」 페이지다
[3] p46  값 일치: 1년, 2년, 3년, 5년
```

`_TOK_LOW` 에 `\d+\s*년` · `\d+\s*개월` 이 값으로 들어 있었고, 부착 조건이
`LOW 두 개 이상`이라 **기간 라벨 두 개만 겹쳐도 인용이 붙었다.** p48 은 자산구성
페이지인데 차트 축에 "최근1년…"이 있어 근거가 됐다. 반대로 답변이 실제로 옮겨 적은
값(35.68 · 20.87 …)이 있는 p47#c011 은 인용에 없었다.

**수정** — 기간 라벨을 `_TOK_PERIOD` 로 분리했다. 클래스코드와 같은 취급이다:
부착 문턱에 세지 않고 정렬에만 쓰며, `unsupported_values` 에도 넣지 않는다.
연도(`2024년`)는 축 이름이 아니라 주장이므로 LOW 에 남긴다 — 9차 P-E5 의 진짜 오류
5건이 그 토큰으로 잡혔다.

**재판정 후 P-E5 인용** (근거 후보 8건)

```
p47#c010  값 일치: 18.96%, 18.99%, 19.2%, 19.33%
p46#c011  값 일치: 1.79%, 10.28%, 10.6%, 2.15%
p47#c011  값 일치: 18.73%, 20.87%, 22.43%, 23.33%   ← 빠져 있던 그 청크
```

### 2-2. `unsupported_values: 0` 은 "다 검증됐다"가 아니었다

9차의 `단위:%` 수정은 **청크 쪽**을 열었다. 그런데 **답변 쪽은 그대로 `%` 를 요구**
하고 있었고, 답변이 표로 쓰면 셀에 `%` 를 안 붙인다.

```
9차 답변   | 종류A-e | -23.33% | 36.13% |  → 토큰 20개 → 20개 플래그
10차 답변  | 종류A-e | -23.33  | 36.13  |  → 토큰 0개  → 0개 플래그
```

같은 표를 옮긴 같은 답변인데 지표가 뒤집힌다. 10차의 0은 **볼 것이 없었다**는 뜻이다.

**수정** — `utils.md_table_rows` / `md_cell_number` 를 만들고, `_tokens()` 가 마크다운
표의 숫자 칸도 청크 쪽과 **같은 기준**(소수점이 있어야 한다)으로 읽는다. 정수 칸
(금액·좌수·연도)은 안 들어온다.

### 2-3. 계산기가 낸 값이 전부 '근거 없는 값'으로 잡히고 있었다

10차 D-B3 은 퇴직소득세 계산 문항이고, 도구가 낸 중간값을 그대로 설명했다.

```
② 근속연수공제 70,000,000원   ③ 환산급여 12,000,000원
⑤ 과세표준 1,600,000원        ⑦ 퇴직소득세 240,000원
```

12개 전부 `unsupported_values` 다. 코퍼스 청크에 있을 리가 없는 값이다.
**10차 32개 중 12개가 이 한 문항**이고, 지표가 가장 근거가 확실한 답변을 최악으로
채점하고 있었다.

**수정** — `attach_citations_by_value(..., extra_text=)` 를 열고 combiner 가
`calc_result` 의 `steps`·`explanation`·숫자를 넘긴다. 여기서 나온 값은 '근거 있는
값'으로 세지만 **인용은 붙지 않는다** — 계산 결과는 출처 목록에 넣을 문서가 없다.

### 2-4. 결과 파일의 답변에서 줄바꿈이 지워지고 있었다

`run_queryset` 이 `truncate()` 로 답변을 적고 있었고, `truncate` 는 줄바꿈을 지운다.
그래서 저장된 답변은 표가 통째로 한 줄이라 사람이 읽기 어렵고, 저장된 답변으로
표 대조를 다시 돌리면 **실행 중과 다른 결과**가 나온다.
길이만 자르는 `clip()` 을 새로 만들어 그걸 쓴다.

## 3. 형제펀드 — 변별자가 겹치는 군이 있었다

`fund_variant()` 는 이름 끝 괄호 안을 변별자로 쓰는데, 형제끼리 **같은** 군이 있다.

```
베어링 고배당 증권 투자회사(주식)      -> 변별자 '주식'
베어링 고배당 증권자투자신탁(주식)      -> 변별자 '주식'
```

이 군에서는 답변이 "베어링 고배당 … 주식형"이라고만 써도 **두 펀드가 모두 지목된
것으로 판정된다.** 지목 판정이 정밀도 가드인데 여기서 열려 버린다.

**수정** — `index.loader.fund_discriminators(name, group)` 를 만들었다. 변별자가
겹치면 상품형태(`투자회사`·`자투자신탁`·`투자신탁`)까지 보고, 그래도 안 갈리면 빈
목록을 돌려준다(= 아무도 특정 못 함, 보수적 동작). 같은 판단을 하는 세 노드
(`answer_generator._named_funds` · `combiner._asset_claim_conflicts` ·
`query_analyzer` 형제 정리)가 전부 이 함수를 쓴다.

## 6. 판단이 필요했던 것

**7-1 근거 게이트는 지금대로 둔다.** "인용 0건 + 전원 검증실패"에 고지를 붙여
내보내면 심사자 입장에서는 근거 없는 답변이다. 지표상 손해라도 거절이 맞다.
(`PENSION_REFUSE_WHEN_NO_EVIDENCE=0` 으로 끌 수 있게는 돼 있다.)

다만 회귀 원인이 **분해 환원으로 서브질문 표현이 달라진 것**이라면 게이트와 별개
문제다. 검증 실행에서 P-G0a·P-F1 의 `sub_questions` 를 9차와 대조해야 한다.

**7-2 고지 문구는 채점에 영향이 없다.** 10차 답변을 골드셋 `must`/`must_any`/
`must_not` 에 실제로 걸어 보면 「※ 위 내용은 자동 검증 단계를…」 문구 자체는 어느
패턴에도 안 걸린다. P-E4 감점은 `must_not` 의 `확인할 수 없습니다` 에 **본문**이
걸린 것으로 고지와 무관하다.

**P-E5 는 골드셋에 없다.** 4개 파일 53문항(dev 35 + holdout 18), 실행 78문항 중
골드셋이 있는 것은 35개다. "카드만 보고 3년까지만 답하면 감점"은 골드셋이 아니라
실행 파일의 `expect` 필드다. 따라서 `must_not` 보강이 아니라 **신규 추가**이고,
평가셋 범위를 넓힐지부터 정해야 한다 — 이번 수정 범위 밖으로 둔다.

## 7. 검증 실행에서 확인할 것

수정이 실행에 반영됐는지, 의도대로 동작했는지 순서대로.

### 반영 확인 (결과 파일만 보면 된다)

- [ ] `rows[*].table_axis_conflicts` 필드가 **존재**한다 (신규 필드)
- [ ] `retrieval[*].detail.stitched` 에 이어붙인 chunk_id 가 찍힌다
- [ ] `answer` 에 줄바꿈이 남아 있다 (`answer.count("\n") > 0`)

### 표적 문항

### 9-2. 결함 ① — 정답이 든 카드를 검색이 가져왔는데 뒤에서 버린다

검증 실행에서 실패한 상품 트랙 7문항의 `retrieval` 분포를 보면 **전부**

그리고 그 카드에는 **기대 답변이 글자 그대로** 적혀 있다.


그런데 답변은 **"제공된 자료에서 이 질문에 답할 근거를 찾지 못했습니다"** 68자다.
채점 단계(`grade_documents`)가 LLM 이라, 그 카드를 "무관"으로 떨어뜨렸다.
전부 탈락하면 근거 0건이 되고 게이트가 거절로 보낸다.
**매 차수 다른 문항이 걸리는 이유가 이것이다** — 판정이 LLM 이라 흔들린다.

#### 수정 — 지목 펀드의 카드는 채점에서 뺀다 (핀 고정)

```python
# nodes/document_grader.py
pinned_names = {n for n in (state.get("filters") or {}).get("fund_name") or [] if n}
pinned = [d for d in docs if d["chunk_type"] in ("fund_card","class_card")
                          and (d.get("fund") or {}).get("name") in pinned_names]
docs = [d for d in docs if d not in pinned]      # 채점 대상에서 제외
...
kept = pinned + kept                             # 채점 결과와 무관하게 맨 앞에
```

**왜 카드만 고정하나** — 펀드카드·클래스카드는 그 펀드 하나를 정리해 만든 **정본**이다.
"이 펀드에 대한 질문"에서 그 펀드의 카드가 무관일 수 없다. 무관 판정이 나오면
채점기가 틀린 것이다. 반대로 섹션 원문은 문서당 88개나 되므로 채점이 걸러 줄
값어치가 있다. 질문이 펀드를 지목하지 않았으면 아무것도 고정하지 않는다.

`applied_filters` 가 아니라 **원래 필터**를 본다 — 완화 2단계는 후보를 넓히려고
`fund_name` 을 비우는 것이지 질문이 그 펀드를 안 말한 게 아니다.

**5문항이 같은 68자 고정 문구로 나간다.** 게이트의 출구가 하나뿐이기 때문이다.

P-E4·P-E1 은 §2 의 카드 고정으로 근거가 살아나므로 **답변 자체가 달라질 가능성이
높다**(카드에 답이 적혀 있다). 나머지 D-F5·D-H3·D-C4 는 게이트 문구를 나누는
별도 작업이 필요하다 — 11차 결과를 보고 판단한다. 지금 같이 손대면 어느 수정이
들었는지 못 가린다.
