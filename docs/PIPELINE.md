# 질문 하나가 지나가는 전 과정

1. 질문("IRP 중도인출 하면 세금 얼마고 서류는 뭐 필요하고 언제까지 내야 해?")에서
   LLM이 **질문유형**과 (있으면) **펀드명**을 뽑는다
2. LLM이 서브질문을 만들고, **서브질문마다 "이건 상품 추천인가?"를 판단**한다
   → 추천이면 `scope="all"`(규정문서+투자설명서), 아니면 `scope="doc"`(규정문서만)
3. 각 서브질문에 대한 문서 검색
   - 실패(임계 미달): scope를 넓혀 재검색 → 그래도 안 되면 필터 전면 해제
   - 성공: 검색된 근거를 추출
4. 각 서브질문의 근거를 LLM으로 재검증 (벡터 검색은 top-k를 무조건 채우므로 무관한 문서가 섞인다)
   - 통과x: 가상답변(HyDE)을 만들어 그 임베딩으로 다시 검색 (질문보다 답변 형태가 실제 문서와 닮았다)
   - 통과: 답변과 인용 출처 생성
5. 답변 채점: 환각 여부와 품질 점검
   - 품질 미달: 근거부터 틀렸을 수 있으므로 재작성+HyDE로 다시 검색
   - 환각: 근거는 맞으므로 답변만 다시 생성
6. 최종 답변: 각 서브질문의 (질문, 답변) 쌍을 LLM에게 줘서 합성

## 필터 설계 — 2026-08 개편

**필터를 8축에서 2축으로 줄였다.** 선행모델을 다시 읽은 결과와 자체 실측이 같은
결론을 가리켰기 때문이다.

### 선행모델(FinSight)이 실제로 한 것

```python
# config.py
METADATA_FILTER_INIT = ["company_name", "year"]

# nodes/document_retriever.py
metadata = {k: v for k, v in metadata.items() if k in metadata_filters}
```

`extract_metadata` 는 `{company_name, year, topics}` 를 만들지만 이 한 줄에서
**topics 가 버려진다.** 청크 쪽 `topic` 은 아예 `"Other"` 하드코딩이고
(`Index/vector_store.py:369`), 답변 프롬프트에서도 명시적으로 제외한다
(`field_to_ignore_from_metadata_for_generation` 에 `"topic"` 이 두 번 적혀 있다).

즉 **주제 태그를 LLM 으로 뽑아놓고 파이프라인 전체에서 쓰지 않는다.**
하드 필터로 쓴 건 문서 앞 10페이지에서 한 번 뽑아 전 청크에 복사한
`company_name`/`year` 둘뿐 — **누락이 구조적으로 불가능한 값**이다.

### 우리 실측 (3,853청크 전체)

| 축 | 실측 | 판정 |
|---|---|---|
| 금융주제 21종 | 상품종류 84.4%, 적립금운용 43.5%, 법령벌칙 42.2% → 변별력 없음.<br>반대로 펀드카드에는 5종만 붙어서, 그 밖의 주제가 필터로 들어오면 **92장 전멸** | 제거 |
| 계좌유형 | **88.7%가 미태깅** → 필터로서 무효 | 제거 |
| 금융목적 | 원본에 `사유` 필드가 없어 항상 `None` (죽은 필터) | 제거 |
| asset_type / risk_grade | 값은 깨끗하나, 추천 질문에서 후보를 과하게 지운다 | 가중으로 강등 |

실제 사고 사례:

```
"연금저축 세액공제 받으며 담을 채권형 펀드 추천"
  → 금융주제=[세액공제] → fund_card 92장 중 0장 통과
  → 전체 1건(ISA 전환 FAQ)만 남는데, 1건이라도 나오면 완화 루프가 안 돈다
  → 그 1건을 근거로 펀드를 추천하는 조용한 오답
```

### 개편 후 필터

| 필터 | 값 | 선행모델 대응 | 결정 시점 |
|---|---|---|---|
| **scope** | `doc` \| `all` | — (우리 코퍼스 고유) | **서브질문마다** LLM 판단 |
| **fund_name** | 실제 92개 목록 안의 값만 | `company_name` | 질의 분석 (선택) |

`scope` 이분법이 유효한 이유는 코퍼스 구성이다. 투자설명서가 전체의 **91%**(3,679/3,853)라,
추천이 아닌 질문에 상품 문서를 열어 두면 제도·절차 문서가 그 밑에 깔린다.
반대로 추천 질문에 규정문서만 보면 펀드 정보가 아예 없다.

`fund_name` 은 선행모델의 `company_name` 과 정확히 같은 성격이다 —
투자설명서 1권 = 펀드 1개이므로 그 문서의 전 청크에 대해 참인 확정값이다.

나머지 신호는 **필터가 아니라 점수 가중**으로 내렸다. 가중은 후보를 지우지
않으므로 잘못 걸려도 순위가 밀릴 뿐 정답이 사라지지 않는다.

| 가중 | 값 | 근거 |
|---|---|---|
| 출처 신뢰도 (`tier`) | doc ×1.0 / prospectus ×0.85 | 규정문서 > 투자설명서 |
| distractor | ×0.35 | 제도 파일 '첨부-관련법령' 37건 |
| 파싱 신뢰도 (`confidence`) | ×confidence | class_cards 좌표 파싱 28건이 0.5~0.55 |
| 표 청크 (`section`이 "표"로 시작) | ×1.25 (계산·사실조회) | 세율표·한도표가 정답인 경우 |

> ⚠️ **`tier` 를 새로 만든 이유**: 원본 JSONL 의 `source` 필드는 doc 문서 일부
> (doc33/53/57/58, 60건)가 `"상품"` 으로 찍혀 있다. 그대로 쓰면 **가장 신뢰도 높은
> 문서가 투자설명서와 같은 취급**을 받아 0.85 감점된다. 그래서
> "장르(corpus)" 와 "출처 신뢰도(tier)" 를 별도 축으로 분리했다.

## 0. 먼저 알아야 할 구조 원리 3개

이 시스템은 **LangGraph** 로 만들어졌다. 파일이 30개 넘지만 전부 셋 중 하나다.

| **State** | 컨베이어 위의 **상자** | `TypedDict` | `state.py` |
| **Node** | **작업대** | `state` 받아 dict 반환하는 함수 | `nodes/` |
| **Edge** | **갈림길 표지판** | 문자열 반환하는 함수 | `edges/` | 노드와 노드를 연결

### ① 노드는 그냥 함수

```python
def grade_documents(state):
    docs = state["documents"]              # 상자에서 꺼내고
    kept = [d for d in docs if ok(d)]      # 일하고
    return {"documents": kept}             # 바꿀 것만 반환
```

state 전체를 반환하지 않는다. **바꿀 키만** 반환하면 LangGraph가 합쳐준다.

### ② 리듀서 — 병렬 실행의 핵심

서브질문 3개를 동시에 처리하면 3개 노드가 같은 키에 쓰기에 값이 덥혀 써지는 걸 막기 위해

```python
qa_pairs: Annotated[List[dict], operator.add]      # add로 이어붙이기
citations: Annotated[List[dict], dedup_citations]  # 합치되 중복 제거하고 합치기
web_used: Annotated[bool, or_bool]                 # 하나라도 True면 True
```
**병렬로 갈라지는 그래프에서 여러 노드가 건드리는 키는 예외 없이 리듀서가 필요.**

### ③ Send — 병렬 fan-out: 서브 질문의 개수만큼 병렬 실행하기

```python
return [Send("rag_worker", {...}) for s in sub_questions]
```

리스트를 반환하면 그 개수만큼 같은 노드가 **동시에 복제 실행**된다.
`Send`(흩뿌리기) + 리듀서(모으기) — 이 한 쌍이 멀티에이전트다.

> 대신 무엇이 빠졌는지는 로그로 반드시 남긴다.

## A-2. 규칙 태그 파생을 삭제한 이유

예전에는 본문 정규식으로 `계좌유형`·`금융주제`·`금융목적` 을 붙이고 **그걸 검색
필터로** 썼다. 3,853청크 전체에 규칙을 돌려 실측한 결과, 셋 다 필터로 쓸 수 없었다.

```
금융주제 태그 빈도 (전체 대비)
  상품종류 84.4%  적립금운용 43.5%  법령벌칙 42.2%  가입절차 30.9%  담보대출 22.5%
  ─ 여기까지 변별력 없음 (투자설명서 본문에 다 걸린다)
  세액공제 0.2%  퇴직소득세 0.1%  연금소득세 0.2%  연금수령한도 0.1%
  ─ 세제 태그는 데이터 자체가 거의 없다

계좌유형: 88.7% 미태깅
금융목적: 원본에 '사유' 필드 없음 → 항상 None
```

`법령벌칙` 42.2%는 `제\d+조` 정규식이 투자설명서 조항 인용에 전부 걸린 오탐이고,
`담보대출` 22.5%는 "담보/대출"이 본문에 흔해서 생긴 868건 오탐이다.

**그리고 펀드카드에는 5종만 붙는다**(상품종류·수수료·수익률·위험등급·적립금운용).
LLM 이 그 밖의 주제를 뽑는 순간 92장이 통째로 배제된다.

선행모델도 같은 결론에 도달해 topics 를 하드 필터에서 뺐다.
→ **만들지 않으면 잘못 걸 일도 없다.** 태그 파생 코드를 통째로 삭제했다.

대신 문서 단위로 확정되는 값만 청크에 박는다 — `tier`, `corpus`, `chunk_type`,
그리고 투자설명서면 `fund_name`/`위험등급`/`자산유형`/`연금저축_가능`/`퇴직연금_가능`.
전부 누락이 구조적으로 불가능한 값이라 하드 필터로 써도 정답이 사라지지 않는다.

검색 점수에 반영되는 신호는 남겼다 (필터가 아니라 **가중**이다).

| 필드 | 값 | 검색에서의 효과 |
|---|---|---|
| `tier` | doc 174 / prospectus 3,679 | ×1.0 / ×0.85 |
| `distractor` | 제도 파일 '첨부-관련법령' **37건** | ×0.35 (지우지는 않음) |
| `confidence` | 0.8 미만 **28건** (class_cards 좌표 파싱) | ×confidence |
| `section` 이 "표"로 시작 | **60건** | 계산·사실조회에서 ×1.25 |

> ⚠️ 예전 문서에 적힌 `origin == "table_row"` **149건은 존재하지 않는다.**
> 현재 데이터에 `origin` 필드가 아예 없어서 표 가산이 한 번도 발동하지 않았다.
> 실제 표는 `section` 이 `"표1"`/`"표2"` 로 들어오므로 그 기준으로 바꿨다.

## A-3. 임베딩 — multilingual-e5-large (로컬 실행)

**파일**: `llm/embeddings.py`, `index/build_index.py`

### 왜 CLOVA clir-sts-dolphin 에서 바꿨나

| | clir-sts-dolphin (기존) | multilingual-e5-large (현재) |
|---|---|---|
| 실행 | CLOVA API 호출 | 로컬 |
| 비용 | 청크당 1회 유료 호출 | 0 |
| 배치 | **한 번에 문장 하나** + sleep | 배치 32 |
| 학습 목적 | 문장 유사도(STS) | **검색(retrieval)** |
| 차원 | 1024 | 1024 (동일) |

1. **과금·레이트리밋이 사라진다.** 3,853청크를 넣으려면 3,853회 유료 호출 + sleep
   이었다. 청킹을 손볼 때마다 전체 재임베딩이 필요한데, 그 비용이 실험 횟수를 제한했다.
2. **검색 특화 모델이다.** e5 계열은 (query, passage) 쌍 대조학습으로 만든 retrieval
   모델이다. STS 모델은 "두 문장이 같은 뜻인가"를 재도록 학습돼서, 짧은 질문 ↔ 긴
   문서 매칭에는 결이 맞지 않는다.

### ⚠️ 접두사가 필수다

```
질의  → "query: 퇴직연금 중도인출 사유"
문서  → "passage: 중도인출 ■ 중도인출 - 근로자퇴직급여보장법 …"
```

비대칭 검색(짧은 질의 ↔ 긴 문서)을 학습할 때 이 접두사로 역할을 구분했기 때문에,
빼면 두 벡터가 같은 공간에 놓이지 않아 성능이 눈에 띄게 떨어진다.

→ `embed_query()` / `embed_passages()` 로 **진입점을 아예 나눠서** 호출부에서
접두사를 빠뜨릴 수 없게 했다.

### ⚠️ 메모리 가드 — 이게 없으면 프로세스가 죽는다

e5-large 는 fp32 가중치만 2.2GB 다. 여유 메모리가 부족한 상태에서 로드하면 파이썬
예외가 아니라 **네이티브 세그폴트(exit 139)** 로 프로세스가 통째로 죽는다.
`try/except` 로는 못 잡는다.

그래서 **로드 전에 여유 메모리를 재고**, 모자라면 아예 시도하지 않고 BM25 단독으로
떨어진다 (`config.EMBED_MEMORY_GUARD`).

```
여유 메모리 부족으로 임베딩을 끕니다 (BM25 단독으로 동작).
  모델=intfloat/multilingual-e5-large  필요≈2800MB  여유=369MB
  해결책 ① 다른 프로그램을 닫고 다시 실행
        ② .env 에서 더 작은 모델로 교체 (차원도 함께 변경)
             PENSION_EMBED_MODEL=intfloat/multilingual-e5-base
             PENSION_EMBED_DIM=768
        ③ 가드를 끄고 강행: PENSION_EMBED_MEMORY_GUARD=false
```

| 모델 | 적재 메모리 | 차원 |
|---|---:|---:|
| `intfloat/multilingual-e5-large` | ~2.4GB | 1024 |
| `intfloat/multilingual-e5-base` | ~1.2GB | 768 |
| `intfloat/multilingual-e5-small` | ~0.55GB | 384 |

모델을 바꾸면 `PENSION_EMBED_DIM` 도 함께 바꾸고 `python -m index.build_index` 로
인덱스를 다시 만들어야 한다.

### 무엇을 임베딩하는가 — 원문이 아니다

`index/loader.py` `searchable_text()` 가 만든 **검색용 텍스트**를 임베딩한다.

```python
파서가 만들어 둔 embed_text 가 있으면 그것을 쓴다   # 펀드명·섹션명이 이미 앞에 붙어 있다
없으면: 섹션 제목 + 본문 + 펀드명 + 자산유형/위험등급
```

- **섹션 제목이 곧 질문인 경우가 많다** (제도 파일: `"임원도 퇴직연금에 가입할 수 있나요?"`)
- 펀드명은 상품 질문의 핵심 키다

BM25 와 벡터가 **같은 텍스트**를 보므로 두 점수를 합칠 때 의미가 어긋나지 않는다.

> 예전에는 여기에 파생 태그(금융주제·계좌유형)도 섞었다. 태그를 없앴으므로 함께 제거했다.

### 캐시

```
cache/emb_multilingual-e5-large.jsonl        문장 해시 → 벡터
cache/vectors_multilingual-e5-large.npy      (3853, 1024) 행렬
cache/vectors_multilingual-e5-large.ids.txt  chunk_id 순서
```

로컬 모델이라 과금은 없지만 캐시는 유지한다 — 3,853건 재계산 시간을 아끼고,
청크를 하나만 고쳐도 그 청크만 다시 계산된다.

### 인덱스에 붙이기

`get_index()` 가 `.npy` 를 읽어 붙인다. 이때 **chunk_id 로 재정렬**한다 —
청크 순서가 바뀌었을 수 있기 때문이다. 불일치하면 경고만 남기고 BM25 단독으로 떨어진다.

```python
norms = np.linalg.norm(mat, axis=1, keepdims=True)
self.vectors = mat / norms        # 미리 정규화 → 이후 내적 = 코사인 유사도
```

미리 정규화해 두면 검색 때마다 노름을 계산할 필요가 없다. 494×1024 = 2MB, 검색 1회 ~5ms.

### 임베딩 추가 필요(api키)

### 질의 쪽 임베딩

검색할 때마다 질의를 임베딩한다 (`nodes/document_retriever.py`).

```python
qvec = _embed(question)                        # 재작성된 질의
hvec = _embed(hyde_doc) if hyde_doc else None  # HyDE 가상 문서 (2-4 참고)
```

임베딩 실패는 **치명적이지 않다** — 로그를 남기고 BM25 로 계속 간다. 검색이 멈추면 안 된다.

### (1) `check_safety` — 안전성·범위 검사

**파일**: `nodes/safety_checker.py` | **LLM**: 1회 (MODEL_PLAN)

### (2) `analyze_query` — 질문유형 + 펀드명 추출

**파일**: `nodes/query_analyzer.py` | **LLM**: 1회 (MODEL_PLAN)

선행모델(FinSight)이 `{회사명, 연도}` 를 뽑던 자리다. **뽑는 것이 둘로 줄었다.**

| FinSight | 우리 | 값 |
|---|---|---|
| category (정량/정성) | **질문유형** | 사실조회 / 계산 / 추천 / 절차 / 혼합 |
| company_name | **fund_name** | 실제 92개 목록 안의 값만 (없으면 빈 배열) |
| filing_year | — | 연금 문서에는 연도 축이 없다 |

`scope` 는 여기서 정하지 않는다. **서브질문마다 다르므로** 분해 단계에서 정한다.
(전역 필터에는 기본값만 넣어 둔다 — 추천이면 `all`, 아니면 `doc`)

**질문유형은 필터가 아니다.** 검색 폭·라우팅·표 가산을 정한다.

```
추천        → top_k 5 → 24
계산/사실조회 → 표 청크(section이 "표"로 시작) ×1.25
계산        → route=calc (계산기 먼저)
```

### ★ 펀드명 목록 주입 — 선행모델의 `db.get_companies()` 대응

프롬프트에 **실제 펀드명 92개를 통째로 넣는다.** 선행모델과 같은 방식이다.

```python
# 선행모델
companies_set = db.get_companies()
metadata_extractor.invoke({"query": question, "company_set": companies_set})

# 프롬프트
"Match the company name mentioned in the query to the parent company in the
 provided list (`company_set`). Ensure that the output is an **exact match**
 with one of the parent company names in the provided list.
 If no match is found ... set company_name to None."
```

```python
# 우리 (nodes/query_analyzer.py)
known = fund_names()                       # index/loader.py, 코퍼스에서 추출
prompts.query_analyzer_system(known)        # 프롬프트에 주입
```

목록을 주지 않으면 LLM 이 "미래에셋 배당주 펀드" 같은 존재하지 않는 이름을
만들어내고, 그 이름으로 필터를 걸면 후보가 0건이 되어 파이프라인이 헛돈다.

**방어는 2중이다.**

| 층 | 무엇 | 대응하는 선행모델 코드 |
|---|---|---|
| 사전 | 프롬프트에 실제 목록 주입 + "exact match" 지시 | `db.get_companies()` |
| 사후 | `_sanitize()` 가 목록 밖 값을 버린다 | `valid_topics = [t for t in topics if t in topics_set]` |

사후 검증에는 승격 규칙도 있다 — 부분 표현("미래에셋퇴직플랜")이 목록의 항목
**하나에만** 매칭되면 정식 명칭으로 올린다. 둘 이상이면 모호하므로 버린다.

**예시**

```
"주택 구입으로 중도인출하려는데 무슨 서류가 필요한가요? 분양받는 경우입니다."
  → 질문유형: "절차",  fund_name: []
     scope 는 분해 단계에서 서브질문마다 결정 → 여기서는 "doc"

"미래에셋퇴직플랜 채권형 총보수 얼마예요?"
  → 질문유형: "사실조회"
     fund_name: ["미래에셋퇴직플랜증권자투자신탁1호(채권)"]   ← 목록에서 승격
```

> **삭제된 것**: `_apply_domain_rules()` (중도인출 소스 보강 규칙 3종).
> 소스 축이 없어졌으므로 보강할 대상도 없다. 예전에는 "IRP 중도인출 사유"의 답이
> 제도·중도인출절차·세제 세 소스에 나뉘어 있어서 규칙으로 억지로 합쳤는데,
> 지금은 `scope="doc"` 하나로 규정문서 전체를 보므로 애초에 나뉘지 않는다.

### (3) `route_query` — 처리 경로 결정

**파일**: `nodes/router.py` | **LLM**: 1회 (MODEL_PLAN)

| route | 조건 | 동작 |
|---|---|---|
| `rag` | 일반 문서 질의 | 바로 분해 |
| `calc` | 숫자 계산이 핵심 | 계산기 먼저, 그 다음 문서 검색 |
| `recommend` | 상품 추천 | 검색 폭을 24로 확대 |
| `out_of_scope` | 도메인 밖 | 안내문 |

**전문가 배정을 뺐다 (2026-08).** 예전에는 소스 5종에 전문가 프롬프트를 1:1로
짝지어 두고 라우터가 배정했는데, 소스 필터를 없애면서 그 짝이 성립하지 않게 됐다.

> **선행모델을 다시 읽어보니** 그쪽도 전문가를 고정하지 않았다.
> `create_persona` 가 질문마다 페르소나를 새로 만들되(`role`/`description` 자유
> 문자열, `Literal` 아님), 만들어진 페르소나는 **검색에 전혀 관여하지 않았다** —
> `rag_e2e.invoke()` 에 넘어가는 건 `question` 하나뿐이다.
> 페르소나는 "어떤 질문을 던질까"만 정하고, 답변은 공용 프롬프트가 만들었다.
>
> 우리도 같은 구조다. 질문을 나누는 일은 분해기가 하고, 답변 프롬프트는
> **검색된 근거의 성격**(규정문서/투자설명서)이 고른다.
> 전문성은 프롬프트가 아니라 근거가 만든다.

**결정론적 보정** — LLM 라우팅은 흔들린다. 질의 분석 결과와 어긋나면 분석을 우선한다.

```python
if 질문유형 == "추천":  route = "recommend"        # LLM이 뭐라 하든
elif 질문유형 == "계산" and route == "rag": route = "calc"
```

### (4) `calc_agent` — 연금 계산기 (route=calc 일 때만)

**파일**: `nodes/calculator.py` + `nodes/pension_tools.py` | **LLM**: 2회

```
① 도구 선택 + 인자 추출   (LLM)   자연어 → 구조화된 숫자
② 계산                    (코드)   pension_tools.py — 재현 가능
③ 결과 설명               (LLM)   숫자 → 자연어
```

**숫자가 만들어지는 지점에 LLM이 없다.** 이게 핵심이다.

| 도구 | 계산 |
|---|---|
| `tax_credit_limit` | 세액공제 한도·절세액 |
| `retirement_income_tax` | 퇴직소득세 (환산급여 5단계) |
| `pension_income_tax` | 연금소득세 (연령별 3.3~5.5%) |
| `early_withdrawal_tax` | 중도인출 세금 (부득이한 사유 여부가 세율을 가름) |
| `withdrawal_limit` | 연금수령한도 = 평가액 ÷ (11-연차) × 120% |
| `future_value` | 적립 예상액 |

세율은 `data/tax_tables.json` 에 있다. **세법이 바뀌면 이 JSON만 고치면 되고 코드도 프롬프트도 안 바뀐다.**

> **선행모델과의 차이**: FinSight는 LLM에게 파이썬 코드를 생성시켜 실행했다.
> 범용 재무지표 21종을 다뤄야 해서 함수를 미리 다 만들 수 없었기 때문이다.
> 우리는 반대로 간다 — 연금 계산은 법으로 공식이 고정돼 있고, 세금 계산을
> LLM이 즉석에서 짠 코드로 하면 검증이 불가능하며, 같은 질문에 매번 다른 코드가
> 나오면 성능 측정도 안 되기 때문이다.

**입력이 부족하면** 지어내지 않고 무엇이 필요한지 되묻는 안내를 답에 넣는다.

```
계산에 필요한 정보가 부족합니다. 다음 값을 알려주시면 계산해 드리겠습니다:
· 퇴직급여 금액
· 근속연수
```

계산 후에도 **문서 검색을 계속한다.** 계산 결과에는 문서 근거가 없으므로 세제 문서를 함께 붙여야 하기 때문이다.

### (5) `decompose` — 질문 분리 에이전트

**파일**: `nodes/question_decomposer.py` | **LLM**: 1회 (MODEL_PLAN)

**왜 쪼개나**: 문서 검색은 질문이 하나의 사실만 물을 때 가장 정확하다.

**규칙**
- 최대 4개 (`MAX_SUB_QUESTIONS`)
- ★ 각 서브질문은 **그것만 읽어도 뜻이 통해야 한다(self-contained)**
- 각각에 `is_recommendation` 을 붙여 **서브질문별로 검색 범위가 달라진다**
- 답이 겹치는 질문 금지

#### ★ 서브질문마다 scope 를 정한다 — 이것이 유일한 하드 필터다

```python
is_recommendation=True   → scope="all"   규정문서 + 투자설명서
is_recommendation=False  → scope="doc"   규정문서만
```

**한 질문 안에서도 갈린다**는 게 핵심이다.

```
"퇴직연금 IRP로 ETF랑 펀드 굴리려는데 어떻게 구성해야 할까?"
  ① "퇴직연금 IRP 계좌에서 ETF 매수가 허용되는 범위는?"        scope=doc  (운용규제)
  ② "퇴직연금 적립금의 위험자산 투자한도는 얼마인가?"          scope=doc  (운용규제)
  ③ "퇴직연금 IRP에 가입 가능한 채권형 펀드는 어떤 것이 있는가?" scope=all  (상품)
```

①②를 `all` 로 열면 투자설명서 3,679건이 운용규제 53건을 덮는다.
③을 `doc` 으로 닫으면 펀드 정보가 아예 없다.

**실측** — "IRP 가입 가능한 채권형 펀드는?" 을 필터 없이 검색하면:

```
48.9 (제도/qa) doc18#p1#c004  "퇴직연금 가입자 교육은 어떤 방식으로..."
47.3 (제도/qa) doc14#p1#c003  "IRP에 돈을 어떻게 입금할 수 있나요?"
47.3 (제도/qa) doc14#p1#c002  "IRP에 누가 가입할 수 있나요?"
  → 상위 5건 전부 제도 Q&A. 펀드카드 0건.
```

"퇴직연금/IRP/가입"이 genre_a 문답에 밀집돼 있어 펀드 질문이 제도 문답으로 빨려간다.
`scope="all"` + top_k 24 를 걸면 fund_card 19건이 잡힌다.

#### 자기완결성이 필터 정제 노드를 대신한다

선행모델은 분해 규칙에서 self-contained 를 강제했다.

```
"Each subquestion should be self-contained with all the information necessary to solve it."
"Each of the decomposed question should be dealing in only a single year"
```

분해 후에도 회사명·연도가 문장에 남으므로, 서브질문에서 필터를 **다시 뽑아도**
같은 값이 나온다. 우리도 같은 규칙을 넣었다.

```
원문: "주택 사려고 중도인출하는데 세금이랑 서류 알려줘"
  ✗ ② "필요한 서류는?"                              ← '주택'이 증발
  ✓ ② "주택 구입 목적 중도인출에 필요한 서류는 무엇인가?"
```

조건이 문장에 살아 있으면 별도의 필터 정제 노드가 필요 없다.
→ **`refine_filters` 노드를 삭제했다. 서브질문 1개당 LLM 호출이 1회 줄었다.**

`fund_name` 은 전역에서 상속한다 — 분해하면 문장에서 빠질 수 있고, 빠졌다고 해서
그 조건이 사라진 것은 아니기 때문이다.

분해가 실패하면(빈 배열) 원 질문 1건으로 진행한다 — 파이프라인이 멈추면 안 된다.

### (6) `rag_worker` — 서브질문별 병렬 처리 ★

**파일**: `workflows/main_graph.py` (어댑터) + `workflows/rag_core.py` (본체)

`edges/decomposition.py` 의 `send_sub_questions()` 가 `Send` 리스트를 반환 → 서브질문 개수만큼 병렬 실행.

`rag_worker` 는 **어댑터**다. `rag_core` 는 `RAGState`(키: `answer`), 최상위는
`OverallState`(키: `qa_pairs`)를 쓰므로 이름을 바꿔 끼운다.
(선행모델의 `map_fields_in_node` 와 같은 역할)

#### 6-1. `retrieve` — 검색

**파일**: `nodes/document_retriever.py`

**하이브리드 검색**
- **BM25**(어휘) : "환산급여공제", "C-P2e" 같은 정확한 도메인 용어·코드에 강함
- **벡터**(의미) : "돈 미리 빼 쓸 수 있나요" ↔ "중도인출" 처럼 말이 다를 때 강함
- 가중치 **0.35 : 0.65** (`config.BM25_WEIGHT` / `VEC_WEIGHT`)

> **왜 벡터 비중을 0.55 → 0.65 로 올렸나**: multilingual-e5-large 는 (query, passage)
> 쌍 대조학습으로 만든 **검색 특화** 모델이라, 문장 유사도(STS) 모델인
> clir-sts-dolphin 보다 의미 매칭이 강하다.
> 다만 BM25 를 0 으로 두지는 않는다 — 클래스 코드(`C-P2e`)나 법령 조문 번호처럼
> **철자가 곧 의미인 토큰**은 여전히 어휘 일치가 이긴다.

한국어 토크나이저(`utils.tokenize_ko`)는 형태소 분석기 없이 **어절 + 한글 2-gram** 을 쓴다.
"중도인출"과 "중도 인출"이 같은 2-gram(중도, 도인, 인출)을 공유하므로 띄어쓰기가 달라도 매칭된다.

**검색 점수에 곱해지는 도메인 가중치** (`store.py` `_weights()`)

| 가중 | 값 | 이유 |
|---|---|---|
| 출처 신뢰도 (`tier`) | doc ×1.0, **prospectus ×0.85** | 규정문서 > 투자설명서 (확정 사항) |
| distractor 감점 | ×0.35 | 제도 파일 '첨부-관련법령' 37건은 들러리 |
| 파싱 신뢰도 | ×confidence | class_cards 좌표 파싱 28건이 0.5~0.55 |
| 표 청크 가산 | ×1.25 (계산·사실조회) | 세율표·한도표가 정답인 경우가 많음 |

> ⚠️ `tier` 로 판단하는 것이 중요하다. `corpus` 로 하면 doc33/53/57/58(60건)이
> 원본 `source="상품"` 때문에 **고신뢰 문서인데 감점**된다.

**top-k 결정**

```python
if 질문유형 == "추천" or filters["scope"] == "all":  return 24   # ★ 넓게
else:                                                return 5
```

> **추천을 왜 넓게 보나**: 추천은 "정답 1개를 찾는" 문제가 아니라 "후보군을 모아 조건으로
> 거르는" 문제다. top-5만 보면 위험등급·자산유형 조건에 맞는 상품이 아예 후보에 없을 수 있다.
> 실측: 골드셋 G011(IRP 채권형 저위험 추천)이 top-5에서 recall 0.00 → top-24에서 **1.00**.

**필터 점진 완화** — 축이 하나뿐이라 완화도 한 단계다.

```python
level 0 : 서브질문이 정한 scope 그대로
level 1 : scope="all"        (투자설명서까지 개방)
level 2 : fund_name 해제
level -1: 필터 전면 해제      ← 선행모델의 무필터 재검색에 대응
```

#### ★ 완화 조건을 '0건'에서 '임계 미달'로 바꿨다

예전 루프는 `if hits: break` 였다. **1건만 나와도 멈춘다**는 뜻인데, 이게 실제로
가장 나쁜 실패를 만들었다.

```
"연금저축 세액공제 받으며 담을 채권형 펀드 추천"
  옛 필터 {source:[상품], 금융주제:[세액공제], asset_type:[채권], 연금저축_가능:True}
    → 후보 1건 (chunks_doc33 ISA 전환 FAQ)
    → 0건이 아니므로 완화 루프 미발동
    → ISA 전환 FAQ 1장을 근거로 펀드를 추천하는 조용한 오답
```

0건이 아니라서 폴백이 안 도는 상황을 막으려면 임계값이 필요하다.

```python
need = min(config.DOCS_RELEVANCE_THRESHOLD + 1, top_k)
...
if len(hits) >= need: break
```

선행모델도 같은 구조였다 — 재시도마다 `metadata_filters.pop()`,
한도를 넘으면 `metadata_filters = []`, 그래도 0건이면 무필터 재검색.

**중요**: 이 완화는 **검색 노드 안에서 한 번의 호출로** 끝난다. LLM 을 부르지 않고,
그래프를 되돌아가지도 않는다. `for level in range(...)` 루프일 뿐이다.
(뒤에 나오는 '재작성'과는 완전히 다른 층위다 — 2-8 참고)

#### 다중 질의 검색 (HyDE 병합)

재작성을 거친 뒤라면 `hyde_doc` 이 State 에 들어 있다. 그러면 **두 질의로 각각 검색**해 합친다.

```python
hits = index.search(question, ...)                    # ① 재작성된 질의
if hyde_doc:
    hyde_hits = index.search(hyde_doc, ...)           # ② HyDE 가상 문서
    hits = _merge_hits(hits, hyde_hits)[:top_k]       # chunk_id 기준 병합, 최고점 유지
```

하나가 실패해도 나머지가 건진다. ⚠️ HyDE 문서는 **검색 질의로만** 쓰이고
`documents` 에는 실제 청크만 들어간다 — 답변 근거로는 절대 넘어가지 않는다.

#### 6-2. `grade` — 문서 관련성 채점

**파일**: `nodes/document_grader.py` | **LLM**: 최대 8회 (병렬)

**왜 필요한가**: 벡터/BM25 검색은 "가장 가까운 k개"를 **무조건** 돌려준다.
5개 전부 엉뚱해도 5개를 준다. 그 상태로 답변을 만들면 환각이 시작된다.

`ThreadPoolExecutor` 로 문서 8개를 **동시에** 채점한다. 순차면 12초, 병렬이면 1.5초.
8건을 넘는 문서(추천 시 24건)는 검색 점수 순서를 믿고 통과시킨다 — 비용 관리.

채점 실패(API 오류)는 문서를 버리는 근거가 못 되므로 **통과 처리**한다.

#### 6-3. 분기 `assess_documents` (`edges/retrieval_check.py`)

| 결과 | 조건 | 다음 |
|---|---|---|
| `enough` | 통과 문서 ≥ 1 | `generate` |
| `rewrite` | 부족 + 재시도 여유 | `rewrite` → `retrieve` |
| `web` | 부족 + 재시도 2회 소진 | `web_search` |

**카운터 없이 조건만 보면 같은 실패를 영원히 반복한다.** `grading_retries` 가 안전장치다.

#### 6-4. `generate` — 답변 생성

**파일**: `nodes/answer_generator.py` | **LLM**: 1회 (MODEL_ANSWER)

**고정 페르소나 5종을 걷어냈다.** 프롬프트는 **근거의 성격**이 고른다.

```python
prospectus = sum(1 for d in docs if d["tier"] == "prospectus")
is_rec = state["is_recommendation"] or prospectus > len(docs) / 2
system = answer_recommend_system if is_rec else answer_system
```

| 프롬프트 | 언제 | 내용 |
|---|---|---|
| `answer_system` | 규정문서 근거 | 제도/세제/절차/운용규제 **주제별 답변 스타일을 한 프롬프트에 담았다** |
| `answer_recommend_system` | 추천 or 투자설명서 과반 | 표 형식(펀드명/자산유형/위험등급/총보수/수익률). **투자권유 아님 고지 필수** |

`answer_system` 안에 예전 전문가 4종의 스타일 지침이 그대로 들어 있다 —
제도는 원칙 먼저·계좌유형별 분기, 세제는 과세 시점 구분·연금수령 vs 연금외수령
세율 차이, 절차는 번호 순서·처리 주체·기한, 운용규제는 한도 수치와 적용 대상.

> **왜 하나로 합쳤나**: 소스 필터가 없어졌으니 "이 질문은 세제 전문가"라고 미리
> 배정할 근거가 사라졌다. 그리고 실제로 한 서브질문의 근거에 제도와 세제가 함께
> 잡히는 일이 흔하다. 전문가를 하나 고르면 나머지 근거를 스타일에서 놓친다.
> 선행모델도 답변 프롬프트는 공용이었다.

**출처 신뢰도 반영 (2중 장치)**
1. 근거 블록에 규정문서를 **앞에** 배치 (`_order_by_trust`, `tier` 기준) — LLM은 앞쪽 컨텍스트에 더 큰 가중을 둔다
2. 프롬프트 규칙에 명시 — "충돌하면 규정문서를 따르고 차이를 알린다"

근거 머리에 출처가 그대로 찍힌다.

```
[1] (출처=규정문서, 분류=운용규제, 섹션=표1, 문서=doc58, p.3)
[2] (출처=투자설명서, 분류=상품, 섹션=펀드요약, 펀드=…, 위험등급=5, 문서=R2_…, p.3)
```

**답변과 인용을 한 번의 호출로 동시에 받는다.**

```python
class GeneratedAnswer(BaseModel):
    main_answer: str
    citations: List[CitationRef]        # [n] 번호 + 인용 문장
    evidence_sufficient: bool
```

답을 만든 뒤 나중에 출처를 역추적하면 정확도가 크게 떨어진다.
인용을 하나도 안 달았으면 상위 3건을 근거로 자동 부착한다 — **출처 없는 답변은 내보내지 않는다.**

#### 6-5. `verify` — 검증 에이전트

**파일**: `nodes/verifier.py` | **LLM**: 2회 (MODEL_VERIFY)

두 검사는 **독립**이며 고쳐야 할 곳이 다르다.

| 검사 | 묻는 것 | 실패 시 |
|---|---|---|
| **환각** (`grounded`) | 근거에 있는 말만 했나 = 틀리지 않았나 | **답변만** 재생성 (검색은 그대로) |
| **품질** (`score`) | 질문에 답했나 = 쓸모 있나 | **질문 재작성 후 재검색** |

근거만 그대로 옮겨 적고 질문엔 답 안 한 답변은 환각 0점이지만 품질 0점이다. 반대도 성립한다.

> **HHEM 미사용** (요구사항). 선행모델은 환각 검사 전용 모델(HHEM)을 별도로 띄웠다.
> 우리는 모델 하나를 더 관리하는 비용 대비 이득이 작다고 보고 LLM 검사로 대체했다.
> 대신 두 검사를 한 노드에 묶어 호출 구조를 단순하게 유지했다.

검증 실패(API 오류)로 답변을 버리면 안 되므로 **통과 처리하고 기록만 남긴다.**

#### 6-6. `rewrite` — 질문 재작성 + HyDE

**파일**: `nodes/question_rewriter.py` | **LLM**: 2회 (재작성 1 + HyDE 1)

**① 용어 정규화 + 동의어 확장** — 연금은 구어체와 문서 용어의 간극이 큰 도메인이다.

```
"돈 미리 빼기"      → "중도인출"
"세금 깎아주는 거"   → "세액공제"
"회사가 넣어주는 돈" → "사용자부담금"
```

동의어를 덧붙인 확장 질의도 함께 만든다: `"중도인출 중간정산 인출 사유 요건"`

**② HyDE (Hypothetical Document Embeddings)** — 가상 문서를 만들어 그걸로도 검색한다.

```
질문:      "연금계좌에서 돈 미리 빼 쓸 수 있나요?"
가상 문서:  "개인형퇴직연금(IRP)은 원칙적으로 만 55세 이전에는 인출할 수 없다.
            다만 근로자퇴직급여보장법 시행령 제14조가 정한 사유에 해당하는 경우
            중도인출이 허용된다. 무주택자인 가입자의 주택 구입, 6개월 이상 요양,
            파산 선고 또는 개인회생절차 개시가 이에 해당한다. …"
```

**왜 되나**

- 벡터 검색은 **질문 벡터와 문서 벡터의 거리**를 잰다. 그런데 질문과 문서는 애초에
  문체가 다르다 — 질문은 짧고 구어체, 문서는 길고 서술형. 가상 문서는 실제 문서와
  형태가 같으므로 벡터 공간에서 훨씬 가깝다.
- **BM25 에도 듣는다.** 가상 문서가 `근로자퇴직급여보장법`, `시행령 제14조`,
  `부득이한 사유`, `기타소득세` 같이 **문서에 실제로 등장하는 용어**를 끌고 오기 때문이다.
  구어체 질문에는 그 단어가 하나도 없다.

**⚠️ 가상 문서는 검색 질의로만 쓴다. 절대 답변의 근거가 아니다.**
LLM 이 지어낸 글이므로 그걸 근거로 답하면 그게 바로 환각이다.
구조적으로 막아 두었다 — `hyde_doc` 은 State 의 별도 필드이고,
`retrieve` 만 그것을 읽는다. `generate` 는 `documents`(실제 검색된 청크)만 본다.

**선행모델과의 차이** — FinSight 도 HyDE 를 썼지만, 재작성 결과와 HyDE 결과를
`xxxxxxxxxx` 라는 구분자로 **한 문자열에 이어붙여** 넘기고 retriever 가 split 했다.
State 에 필드를 추가하기 싫어서 쓴 꼼수다. 우리는 `hyde_doc` 필드로 명시적으로 넘긴다.
같은 효과인데 읽기 쉽고, 실수로 근거에 섞일 위험이 없다.

**실패해도 죽지 않는다** — HyDE 생성이 실패하면 경고만 남기고 재작성 질의만으로 검색한다.

#### 6-7. `web_search` — 네이버 웹 검색 (최후의 수단)

### (6-8) ★ 실패 복구는 **3층 구조**다 — 헷갈리기 쉬운 지점

"검색이 실패하면 다시 한다"는 말이 세 군데에 나오는데, **서로 다른 층위**다.
층을 섞으면 "답변 점수가 낮으면 새 서브질문을 만드나?" 같은 오해가 생긴다. (답: 아니다)

| | 1층 · 필터 완화 | 2층 · 재작성 + HyDE | 3층 · 잔여 재분해(RRR) |
|---|---|---|---|
| **어디서** | `retrieve` 노드 **안** | `rag_core` 서브그래프 루프 | `main_graph` 순환 |
| **무엇이 실패?** | 검색 결과 **0건** | 문서 채점 미달 / 답변 품질 미달 | 원 질문에 **빠진 축**이 있음 |
| **무엇을 바꾸나** | **필터**를 푼다 | **질의 문장**을 바꾼다 | **새 서브질문**을 만든다 |
| **질문이 바뀌나** | ✗ 그대로 | ✓ 재작성됨 (의도는 유지) | ✓ 완전히 다른 질문 |
| **LLM 호출** | **0회** | 2회 (재작성+HyDE) | 1회 (재분해) |
| **한도** | 완화 8단계 | `MAX_GRADING_RETRIES=2` / `MAX_VERIFY_RETRIES=1` | `MAX_ROUNDS=2` |
| **넘으면** | 소스까지 해제 | 웹 검색 폴백 | 종료 |

```
┌─ 3층: RRR ────────────────────────────────────────────────────┐
│  decompose → [서브질문 A][서브질문 B] → aggregate              │
│                    │          │                                │
│    ┌───────────────┘          └──────────┐                     │
│    ▼                                      ▼                    │
│  ┌─ 2층: rag_core (서브질문 A 전용) ──────────────────┐        │
│  │   retrieve ──────────────────────┐                 │        │
│  │      │  ┌─ 1층: 필터 완화 ─────┐ │                 │        │
│  │      │  │ 0건? → 조건 하나 품  │ │                 │        │
│  │      │  │ 반복 (LLM 0회)       │ │                 │        │
│  │      │  └──────────────────────┘ │                 │        │
│  │      ▼                            │                 │        │
│  │   grade ── 미달 ──▶ rewrite+HyDE ─┘                 │        │
│  │      │                            ▲                 │        │
│  │      ▼                            │                 │        │
│  │   generate ──▶ verify ── 품질미달 ┘                 │        │
│  │                  │  └─ 환각 ──▶ generate (재생성)   │        │
│  │                  ▼ 통과                              │        │
│  └──────────────────┴──────────────────────────────────┘        │
│                     ▼                                           │
│  aggregate → check_sufficiency ── 부족 ──▶ decompose_residual ──┤
│                     │ 충분                                      │
└─────────────────────▼───────────────────────────────────────────┘
```

**핵심 구분**

- **2층은 "같은 질문을 다르게 물어본다"** — 서브질문 A 에 대한 답을 못 얻어서
  A 를 재작성해 다시 검색한다. A 라는 질문 자체는 여전히 유효하다.
- **3층은 "물어보지 않은 것을 물어본다"** — A 와 B 의 답은 잘 얻었는데,
  원 질문에는 C 라는 축이 있었다. 그래서 C 를 새로 만든다.

**답변 품질 미달(2층)에서 새 서브질문을 만들지 않는 이유**: 품질 미달은
"이 질문에 대한 근거가 부족했다"는 뜻이지 "다른 질문이 필요하다"는 뜻이 아니다.
새 질문을 만들면 원래 물었던 것이 영영 답 없이 남는다.

### (8) `check_sufficiency` — RRR의 종료 조건

**파일**: `nodes/question_decomposer.py` | **LLM**: 1회 (MODEL_VERIFY)

원 질문과 지금까지 모은 QA 쌍을 보고 **빠진 축이 있는지** 판정한다.

**RRR (Recursive Residual Resolution)**

```
1라운드: 질문 → 서브질문 N개 → 병렬 RAG → 취합 → 충분?
         ↓ 부족
2라운드: 못 답한 부분만 재분해 → 병렬 RAG → 취합 → 종료
```

#### 새 서브질문 생성(`decompose_residual`)은 무슨 과정인가

LLM 에게 **세 가지를 함께 준다.**

```
[원 질문]        "IRP 중도인출 하면 세금 얼마고 서류는 뭐 필요하고 언제까지 내야 해?"
[이미 답한 질문]  - IRP 중도인출 시 적용되는 세율은?
                 - IRP 중도인출 신청에 필요한 서류는?
[부족 판정 사유]  "제출 기한에 대한 정보가 빠짐"
```

→ LLM 이 남은 공백만 새 질문으로 만든다.

```
③ "중도인출 증빙서류 제출 기한은 언제까지인가?"   source_hint: 세제
```

**중복 방지 2중 장치**
1. 프롬프트로 "이미 답한 내용을 다시 묻지 마라" 지시
2. 코드로 `asked_history` 와 대조해 같은 문장 제거 (LLM 이 지시를 어겨도 걸러진다)

새 서브질문도 1라운드와 **똑같이** `Send` 로 병렬 실행되고, 똑같이 필터를 상속받고,
똑같이 2층(재작성+HyDE)·1층(필터 완화) 복구를 쓴다. 라운드만 다를 뿐 경로는 동일하다.

일반 분해와의 차이: 한 번 쪼개고 끝내지 않고 **빠진 축을 스스로 찾아 메운다.**

주의: 답변이 "확인되지 않습니다"라고 해서 곧바로 부족 판정하지 않는다.
자료에 없는 정보는 더 검색해도 안 나온다. **질문의 축 자체가 누락된 경우**에만 반복한다.

**한도 3중 장치**
- 라운드 수 (`MAX_ROUNDS=2`)
- LLM 호출 예산 (`LLM_CALL_BUDGET=40`)
- `recursion_limit=60`

> **선행모델과의 차이**: FinSight는 LangGraph가 정적 그래프라 `decomposer_node_1/2/3`,
> `rag_1/2/3_time`, `aggregate1/2/3` 를 **손으로 3벌 복제**했다.
> 우리는 순환 엣지로 처리해 노드 수가 1/3이고 라운드 수를 config로 바꿀 수 있다.

### (9) `strategy_agent` — 전략 에이전트

**파일**: `nodes/strategy.py` | **LLM**: 1회 (MODEL_ANSWER)

라우터가 `needs_strategy=True` 로 판정했을 때만 돈다 (추천/혼합/비교 질문).

**왜 답변 생성과 분리했나**
- 검색 답변 = "문서에 뭐라고 쓰여 있나" (사실 재현)
- 전략 = "그래서 나는 뭘 해야 하나" (비교·판단)

한 프롬프트에 섞으면 모델이 사실과 의견을 뒤섞어 **환각 검사가 무력해진다.**

```python
verified = [p for p in qa_pairs if p.get("verified", True)]
```

**안전장치**: 새 사실 생성 금지 / 개별 상품 매수·매도 권유 금지 / 전제 조건 명시 강제
("총급여 5,500만원 이하라면 …, 초과라면 …") / 근거 부족 시 전략 제시 거부

### (10) `combine_answer` — 최종 합성

**파일**: `nodes/combiner.py` | **LLM**: 1회 (**항상**)

#### 왜 항상 LLM 을 태우나

서브답변이 1건이어도 LLM 합성을 건너뛰지 않는다. 선행모델의 `combine_answer_v3` 와 같다.

서브답변은 **"그 서브질문에 대한 답"**이지 **"사용자 질문에 대한 답"**이 아니기 때문이다.
예를 들어 사용자가 `"IRP 중도인출 사유가 뭔가요?"` 라고 물었는데 서브답변이
표 행을 그대로 나열한 상태라면, 합성 단계에서 결론 → 조건 → 주의사항 순으로
재구성해야 비로소 답이 된다.

호출 1회가 늘지만 **답변 형태의 일관성**이 훨씬 중요하다.
합성이 실패하면(빈 응답) 서브답변을 이어붙여 폴백한다 — 답을 못 내는 것보다 낫다.

프롬프트에 **사용 가능한 근거 번호 목록**을 함께 넘겨 없는 번호를 만들어내지 못하게 막는다.

#### 인용 번호 재매핑 — 여기가 까다롭다

서브질문마다 독립적으로 답을 만들었으므로 각 답변의 `[1] [2]` 는 **그 서브질문의 근거 목록 기준**이다.
세 개를 이어붙이면 `[1]` 이 세 번 나오고 각각 다른 문서를 가리킨다.

```
서브답변1의 [1][2] → [1][2]
서브답변2의 [1][2] → [3][4]
서브답변3의 [1]    → [5]        (단, 같은 chunk_id면 기존 번호 재사용)
```

정규식으로 **한 번에** 치환한다. 순차 치환하면 `[1]→[3]` 후 `[3]→[5]` 처럼 연쇄된다.

> 선행모델은 최종 답변에 다시 LLM을 태워 인용을 재삽입했는데, 그러면 인용이 원래 문장과
> 어긋나는 일이 생긴다. 문자열 치환이 안전하다.

#### 합성 규칙
- 서브질문 순서가 아니라 **읽기 좋은 순서**로 재구성 (결론 → 근거·조건 → 절차/숫자 → 주의사항)
- 인용 번호 `[n]` 는 그대로 유지, 제시된 번호 외에는 사용 금지
- 충돌 시 규정 문서 우선 + 충돌 사실 한 줄 고지
- **새로운 사실 추가 절대 금지** — 주어진 답변들의 재구성만

#### 자동 부착 (코드가 붙인다, LLM 이 아니다)
- 상품 근거가 섞였으면 → 투자권유 아님 고지
- 상품 + 규정 문서 근거가 함께 있으면 → 소스 우선순위 고지
- 출처 목록

```
### 출처
[1] 소스: 중도인출절차 / 「구입유형별 필수서류 - 주택분양」 — doc49 p.1
[2] 소스: 세제 / 「연금수령한도 안내」 — doc20 p.1
[3] 소스: 상품 / 한국투자골드플랜연금증권전환형자투자신탁1호(채권) / 「펀드요약」 — R2_KR5113420013 p.5
```

## 3. 시나리오 4개 — 실제 실행 트레이스

### 시나리오 A — 단순 사실조회 (소스 보강 규칙 작동)

> **"IRP에서 중도인출이 가능한 사유가 뭔가요?"**

```
 1. check_safety        통과
 2. analyze_query       질문유형=사실조회, scope=doc
 3. route_query         route=rag
 4. decompose           1개로 분리 (추천 0건)
 5. retrieve            5건 (top_k=5, scope=doc, 완화 없음)
                          분포={'doc/qa': 4, 'doc/procedure': 1}
 6. grade_documents     5건 채점 → 5건 통과
 7. generate_answer     [general] 인용 2건, 근거충분=True
 8. verify              통과 — 근거일치=True, 점수=0.85
 9. aggregate           라운드0 — QA 1건 (근거확보 1)
10. check_sufficiency   충분
11. strategy_agent      불필요 → 건너뜀
12. combine_answer      LLM 합성 — 서브답변 1건 + 출처 2건
```

출처:
```
[1] 소스: 제도 / 「개인형 퇴직연금제도(IRP)도 중도인출이 가능한가요?」 — doc14 p.2
[2] 소스: 절차 / 「중도인출」 — doc22 p.1
```

> **설계 변경 이력**: 예전에는 이 질문의 답이 제도·중도인출절차·세제 **세 소스에
> 나뉘어** 있어서, LLM 이 하나만 고르면 답이 반쪽이 됐다. 그래서
> `_apply_domain_rules()` 로 "사유/가능" 어휘를 보고 소스를 강제 보강했다.
> 지금은 `scope="doc"` 하나로 규정문서 전체를 보므로 **애초에 나뉘지 않는다.**
> 보강 규칙 3종을 전부 삭제했다.

> **"IRP 중도인출 하면 세금 얼마고 서류는 뭐 필요해?"**

**서브질문으로 나눠 각각 검색한다**는 점이 핵심이다. 한 번에 검색했다면

동일한 `company_name==apple && year==2023` 필터를 갖고도 서로 다른 청크를 가져오던
것과 같은 원리다 — 필터는 범위를 정하고, 임베딩이 그 안에서 순위를 매긴다.

#### ★ 이 질문이 옛 필터에서 어떻게 실패했는가

이 문서에서 가장 중요한 변경 사례다.

| | 옛 필터 (8축) | 현재 (scope) |
|---|---|---|
| 필터 | `{source:[상품], 금융주제:[세액공제], asset_type:[채권], 연금저축_가능:True}` | `{scope:"all"}` |
| 후보 | **1건** (chunks_doc33 ISA 전환 FAQ) | 3,853건 → top 24 |
| fund_card | **0 / 92** ← 전멸 | **19건** |
| 완화 루프 | 미발동 (0건이 아니라서) | 불필요 |
| 결과 | ISA 전환 FAQ 를 근거로 펀드 추천 = **조용한 오답** | 정상 |

`금융주제=[세액공제]` 하나가 펀드카드 92장을 통째로 지운다. 펀드카드에 붙는
주제 태그는 5종(상품종류·수수료·수익률·위험등급·적립금운용)뿐이라 교집합이 0이기
때문이다. 그리고 1건이 남아서 완화 루프가 돌지 않는다.

같은 유형의 실패가 셋 더 있었다.

```
"IRP 중도인출 되는 펀드 있어?"       금융주제=[중도인출]   → 전체 0건
"연금수령한도 안에서 굴릴 상품 추천"  금융주제=[연금수령한도] → 전체 0건
```

## 4. 설계 근거 정리 — 왜 이렇게 했나

| 결정 | 이유 |
|---|---|
| **필터를 scope 1축으로** | 선행모델도 하드 필터는 `company_name`/`year` 둘뿐이었고 topics 는 화이트리스트에서 뺐다. 필터는 질문 쪽·청크 쪽 값이 **둘 다 100% 신뢰 가능할 때만** 성립한다 |
| **금융주제·계좌유형·금융목적 제거** | 실측: 상품종류 84.4%로 변별력 없음 / 계좌유형 88.7% 미태깅 / 금융목적은 원본 필드 부재로 항상 None. 게다가 펀드카드 92장을 통째로 지우는 사고를 냄 |
| **tier 를 source 에서 분리** | 원본 `source` 가 doc33/53/57/58(60건)을 "상품"으로 찍어 놔서, 그대로 쓰면 **고신뢰 문서가 0.85 감점**된다 |
| **scope 를 서브질문마다 판단** | 투자설명서가 코퍼스의 91%. 추천 아닌 질문에 열면 규정문서가 묻히고, 추천 질문에 닫으면 펀드 정보가 없다. 한 질문 안에서도 갈린다 |
| **fund_name 목록 프롬프트 주입** | 선행모델의 `db.get_companies()` 대응. 없는 이름으로 필터를 걸면 후보 0건 → 파이프라인이 헛돈다 |
| **전문가 고정 해제** | 소스 축이 없어져 짝지을 대상이 소멸. 선행모델도 페르소나를 고정하지 않았고, 페르소나가 검색에 관여하지도 않았다. 프롬프트는 근거의 성격이 고른다 |
| **`refine_filters` 노드 삭제** | 정제할 축이 없다. 선행모델이 서브질문마다 필터를 다시 뽑을 수 있었던 건 self-contained 강제 덕분 — 그 규칙을 분해 프롬프트로 옮겼다. 서브질문당 LLM 1회 절약 |
| **완화 조건을 0건 → 임계 미달** | `if hits: break` 는 1건만 나와도 멈춘다. 실제로 ISA FAQ 1장으로 펀드를 추천하는 조용한 오답이 났다 |
| **추천만 top-k 24** | 추천은 후보군을 모아 조건으로 거르는 문제. G011이 top-5에서 recall 0.00 → top-24에서 1.00 |
| **투자설명서 ×0.85 감점** | 규정 문서 > 투자설명서 (확정 사항). 같은 유사도면 규정 문서가 위로 |
| **distractor ×0.35** | 제도 파일 '첨부-관련법령' 37건은 들러리. 지우지 않고 감점만 (법령 원문이 진짜 답인 질문도 있음) |
| **confidence 가중 추가** | class_cards 좌표 파싱 28건이 0.5~0.55. 표가 어긋났을 수 있으니 순위를 민다 |
| **표 판정을 origin → section** | `origin` 필드가 데이터에 아예 없어 표 가산이 **한 번도 발동하지 않았다**. 실제 표는 `section="표1"` |
| **임베딩을 e5-large 로컬로** | 과금·레이트리밋 제거 → 재임베딩이 자유로워 실험 횟수 제한이 사라진다. 검색 목적으로 학습된 모델이라 STS 모델보다 결이 맞는다 |
| **벡터 0.55 → 0.65** | e5 는 retrieval 학습 모델. 단 BM25 를 0 으로 두지 않는다 — 클래스 코드·조문 번호는 철자가 곧 의미다 |
| **임베딩 메모리 가드** | 모자란 상태로 로드하면 예외가 아니라 **세그폴트로 프로세스가 죽는다.** try/except 로 못 잡으므로 로드 전에 잰다 |
| **모델 티어링 (DASH/HCX-005)** | 판정·분류형 호출이 질문당 대부분을 차지하는데 출력이 짧고 정답 공간이 좁다. 생성·검증만 큰 모델 |
| **계산은 코드가** | 세법 공식은 고정. LLM 생성 코드는 검증 불가 + 실행마다 달라져 측정 불가 |
| **전략을 답변과 분리** | 사실과 의견이 섞이면 환각 검사가 무력해짐 |
| **HyDE 사용** | 연금은 구어체("돈 미리 빼기")와 문서 용어("중도인출")의 간극이 크다. 가상 문서가 문서 어휘를 끌고 와 BM25·벡터 양쪽에 듣는다. 재작성 질의와 **병합 검색** |
| **HyDE 를 근거로 쓰지 않음** | LLM 이 지어낸 글이므로 근거로 쓰면 그게 환각. State 필드를 분리해 구조적으로 차단 |
| **HHEM 미사용** | 모델 하나 더 관리하는 비용 대비 이득이 작음 (요구사항) |
| **합성은 항상 LLM** | 서브답변은 "서브질문에 대한 답"이지 "사용자 질문에 대한 답"이 아님. 1건이어도 재구성 필요 |
| **순환 엣지로 RRR** | 노드 3벌 복제 대신 순환 → 노드 1/3, 라운드 수 설정 가능 |
| **인메모리 인덱스** | 3,853청크 고정 + 배포 단계 아님. Pathway 서버는 과잉 |
| **빌드/서빙 분리** | 임베딩은 비싸고 검색은 싸다. 아티팩트로 못 박아 한 번만 계산 |
| **지문으로 아티팩트 검증** | 청크 증감뿐 아니라 본문 수정까지 잡는다. 낡은 벡터로 조용히 도는 것이 최악 |
| **필수 코퍼스 파일 누락은 실패** | 조용히 건너뛰면 그 주제에 근거 없는 답이 나간다. 침묵이 에러보다 비싸다 |

## 5. 성능 측정 방법

### 측정 순서 — 아래 단계부터 확정하고 올라간다

검색이 정답 청크를 못 가져오면 그 뒤 단계를 아무리 고쳐도 정답이 안 나온다.

```bash
python -m eval.runner --retrieval-only      # 1단계: 검색 (LLM 0회, 무료)
```

```bash
python -m eval.runner --no-llm-judge        # 2단계: 파이프라인 경로·비용
```

```bash
python -m eval.runner --tag full            # 3단계: 정확도까지 전부
```

### 지표 3층

| 층 | 지표 | 필요 | 신뢰도 |
|---|---|---|---|
| **1층** | Recall@k, Precision@k, MRR, Hit / 라우팅 정확도 / 지연·**질문당 토큰** / 근거확보율·검증통과율·웹폴백률 | 없음 | 높음 (결정론적) |
| **2층** | Correctness, Faithfulness | LLM | 중간 (LLM 심판) |
| **3층** | Response Relevancy | 임베딩 | 중간 |

1층이 가장 믿을 만하다. **우리 데이터는 `chunk_id` 가 확정돼 있어서 검색 지표를 정확히 잴 수 있다** —
선행모델은 PDF 파싱 결과라 레벤슈타인 거리로 근사해야 했다.

> `source_accuracy` 지표는 제거했다 — 소스 축 자체가 없어졌다.
> 대신 각 행에 `scope` 와 `tokens_in`/`tokens_out`/`tokens_total` 이 들어간다.

### 골드셋 (2026-08-22 교체)

예전 `eval/goldset.jsonl`(13건)은 삭제했다 — 상당수가 지금 코퍼스에 없는
청크를 정답으로 지목해 recall 이 구조적으로 0 이었다.

지금은 `eval/gold/` 의 확정 형식을 쓴다 (`policy.jsonl` / `product.jsonl`).
정답 조건과 **채점기는 평가 담당이 소유한다** — 이 저장소는 파이프라인을
돌려 `*.compact.jsonl` 실행 기록만 낸다.

```bash
python -m eval.runner --gold --split dev --tag baseline
```

### ablation 실험 설계

`config.WORKFLOW_SETTINGS` 를 바꿔가며 `--tag` 를 다르게 주고 돌린다.

| 실험 | 설정 | 측정 목적 |
|---|---|---|
| `baseline` | grade_documents=F, check_hallucination=F, grade_answer=F | 순수 검색+생성 기준선 |

| `+verify` | check_hallucination=T, grade_answer=T | 검증의 기여 |
| `+hyde` | rewrite_with_hyde=T | HyDE 의 기여 (재작성 경로에서만 발동) |
| `+rrr` | repeat_residual=T, MAX_ROUNDS=2 | 잔여 재분해의 기여 |
| `+embed` | `index.build_index` 실행 후 | 하이브리드 검색의 기여 |
| `scope` | `--retrieval-only` 의 nofilter vs scopefilter | **scope 필터의 기여** |

## 부록 A — LLM 호출 횟수와 모델 배정 (질문 1건 기준)

| 단계 | 호출 | 모델 | 성격 |
|---|---:|---|---|
| check_safety | 1 | **PLAN** (DASH) | 판정 |
| analyze_query | 1 | **PLAN** (DASH) | 분류 |
| route_query | 1 | **PLAN** (DASH) | 분류 |
| decompose | 1 | **PLAN** (DASH) | 판정 |
| calc_agent (계산 질문만) | 2 | PLAN + ANSWER | 추출 + 설명 |
| **서브질문당** — grade_documents | 최대 8 (병렬) | **GRADE** (DASH) | 이진 판정 |
| **서브질문당** — rewrite + HyDE (실패 시) | 최대 2×2 = 4 | **PLAN** (DASH) | 생성이지만 검색용 |
| **서브질문당** — generate | 1 | ANSWER (HCX-005) | 생성 |
| **서브질문당** — verify | 2 | VERIFY (HCX-005) | 검증 |
| check_sufficiency | 1 | VERIFY (HCX-005) | 판정 |
| decompose_residual (RRR 반복 시) | 1 | **PLAN** (DASH) | 판정 |
| strategy_agent (필요 시) | 1 | ANSWER (HCX-005) | 생성 |
| combine_answer | **1 (항상)** | ANSWER (HCX-005) | 생성 |

단순 질문 ≈ **8~15회**, 복합 질문(서브 3개 + 2라운드) ≈ **35~48회**.
`LLM_CALL_BUDGET=40` 이 상한이며, 초과하면 RRR 라운드를 중단한다.

### 모델 티어링을 어떻게 나눴나

CLOVA Studio Chat Completions v3 가 제공하는 모델은 둘이다 — `HCX-005`(고성능,
비전 포함)와 `HCX-DASH-002`(경량). 호출을 성격으로 가르면 이렇게 갈린다.

| | 판정/분류형 | 생성/검증형 |
|---|---|---|
| 예 | 안전성, 분해, 추천여부, 문서채점, 재작성, HyDE | 답변, 환각·품질 검증, 전략, 합성 |
| 출력 | 몇 단어 ~ 몇 줄 | 수백~수천 자 |
| 정답 공간 | 좁다 (enum, bool, 짧은 문장) | 넓다 |
| 호출 수 | **많다** (질문당 8~10회) | 적다 (질문당 4~6회) |
| 배정 | **HCX-DASH-002** | **HCX-005** |

**문서 채점을 내린 효과가 가장 크다.** yes/no + 한 줄 사유가 전부인데 호출 수는
문서 수만큼(질문당 최대 8회) 늘어난다.

구조화 출력 **복구 호출**도 항상 경량 모델로 보낸다 — 내용은 그대로 두고 JSON
형식만 고치는 작업이라 큰 모델을 쓸 이유가 없다.

**HyDE 를 켜면 재작성 1회당 호출이 1 → 2로 는다.** 다만 재작성은 검색이
실패했을 때만 도는 경로이고 둘 다 DASH 이므로 비용 증가는 작다.

### CLOVA Studio 의 다른 API 를 쓰지 않은 이유

| API | 판단 |
|---|---|
| **Re-ranker** (`/v1/api-tools/reranker`) | `grade_documents` 를 대체할 수 있고 토큰도 아낀다. 다만 응답이 "관련 문서 선별 + 요약 압축"이라 **인용 번호↔청크 매핑이 끊긴다.** 우리는 출처 없는 답변을 내보내지 않는 것이 요구사항이라 보류 |
| **Router** | 콘솔에서 도메인을 사전 등록해야 한다. `route_query` 하나를 대체하는데 외부 설정 의존이 생긴다. 교체 시 `nodes/router.py` 한 함수만 고치면 되므로 나중에 재검토 |
| **Segmentation** | 청킹이 이미 끝나 있다 |
| **Embedding v2** | 로컬 e5 로 대체 (과금·레이트리밋 제거) |
| **Tokenizer** | **쓴다** — 아래 부록 B |

## 부록 B — 질문당 토큰 계측

두 가지 방식을 함께 둔다.

### ① 사후 집계 (기본, 추가 호출 0)

Chat Completions 응답의 `result.usage` 를 그대로 `CallLog` 에 쌓는다.

```python
usage = result.get("usage") or {}
return msg, usage.get("promptTokens", 0), usage.get("completionTokens", 0)
```

`llm.mark_question(qkey)` 로 구간을 끊으면 **질문 1건이 쓴 토큰**만 뽑을 수 있다.

```python
result = run(q, qkey=case["qid"])
result["usage"]      # {calls, in_tokens, out_tokens, total_tokens, by_stage, by_model}
llm.usage_by_question()   # 질문별 전체 내역
```

CLI 출력:

```
질문 1건 토큰: 총 9,137  (입력 7,982 + 출력 1,155)  |  LLM 호출 14회  |  12.4초
  모델별
    HCX-DASH-002      9회    4,211 토큰 (46.1%)    5,120ms
    HCX-005           5회    4,926 토큰 (53.9%)    7,280ms
  단계별
    grade_doc          5회   1,980ms  in= 3,102 out=  180 total=  3282
    answer:general     1회   2,410ms  in= 1,845 out=  520 total=  2365
    ...
```

### ② 사전 계산 (옵션, CLOVA Tokenizer API)

```
POST /v1/api-tools/chat-tokenize/{modelName}
요청 {"messages":[{"role","content"}]}
응답 {"result":{"messages":[{..., "count": <int>}]}}
```

`usage` 는 **호출한 뒤에야** 알 수 있다. 토크나이저 API 는 **호출 전에** 입력 토큰을
잰다. 프롬프트를 고쳤을 때(예: 펀드명 92개를 주입했을 때) 입력 토큰이 얼마나 늘지
미리 확인하고, 컨텍스트 한도를 넘기지 않는지 사전에 점검하는 용도다.

```bash
PENSION_PRECOUNT_TOKENS=true   # 호출이 2배가 되므로 필요할 때만
```

실패해도 파이프라인을 막지 않는다 — 계측은 부가 기능이다.
