## 1. 형제펀드가 검색에서 통째로 배제되던 문제 — 이슈 3

**원인은 인용이 아니라 검색이었다.** P-B1 답변이 채권 펀드 수익률을 국공채 값
(5.91%)으로 적은 이유는 모델이 지어내서가 아니라 **채권 펀드 문서가 후보에 아예
없어서**였다.

```
match_known_fund()  … 접두어가 가장 긴 것 하나만 반환
                      형제 셋은 접두어가 동점 → `if k > len(best)` 로 첫 하나만 남음
store._passes()     … fund_name 은 배제형 필터
                      → 나머지 형제 문서가 검색 후보에서 사라짐
```

| 파일 | 수정 |
|---|---|
| `index/loader.py` | `fund_core()` / `fund_variant()` / `sibling_funds()` 신설 — 이름 규칙을 한 곳으로 모았다. `match_known_funds()` 가 동점 형제를 **전부** 반환 |
| `nodes/query_analyzer.py` | `_resolve_siblings()` — 질문이 변별자를 적었으면 그 하나로 **좁히고**, 안 적었으면 형제 전부로 **넓힌다**. `_sanitize` 도 형제군이면 후보를 안 버린다 |
| `nodes/document_retriever.py` | `_ensure_named_fund_cards()` — 질문이 이름을 댄 펀드의 카드가 자리 싸움에 밀리면 채워 넣는다 (상한 `MAX_SIBLING_FUNDS`) |
| `nodes/answer_generator.py` | `_named_funds()` — 형제군에서는 변별자까지 맞아야 "답변이 그 펀드를 말했다"고 본다. `_sibling_notice()` — 근거에 형제가 섞였으면 이름·등급·자산유형을 프롬프트에 못 박는다 |


## 2. 클래스코드만 겹쳐 붙던 인용 — 이슈 2

`_TOK_HIGH` 에 클래스코드가 들어 있어 `if mh or len(ml) >= 2` 가 **C-e 하나로**
통과했다. P-E5 인용 3건이 전부 이 경로였다.

**그런데 무조건 빼면 안 된다.** 9차 값대조 인용 74건으로 재생해 보니 26건(35%)이
날아가고 그중 14건이 P-C 트랙 — **클래스가 질문의 주제인 문항들**이었다.
거기서는 C-P 가 적힌 청크가 정당한 근거다.

그래서 기준을 "코드가 답변에 나왔나" 가 아니라 **"질문이 클래스를 묻나"** 로 잡았다
(`_class_is_topic`). 코드가 질문에 있거나 질문이 "클래스/종류형" 을 부르면 값으로
세고, 아니면 이름표로 본다.

**실측 (9차 값대조 인용 재생, 판정 가능 74건)**

```
무조건 제외      유지 48 / 탈락 26   ← P-C 트랙 14건 손실
질문 기준(채택)  유지 62 / 탈락 12   ← P-E5(3) · P-B1(2) · P-B2 · P-B4 ·
                                       P-D2(2) · D-G2 · D-G3(2)
아래 9번 반영 후  유지 65 / 탈락 9    ← P-E5 3건이 **진짜 값 근거로** 복구됨
```

탈락 9건은 전부 질문과 무관하게 이름표만 겹친 것이다. 클래스코드는 부착 문턱에서
빼되 **정렬 우선순위에는 남긴다** — 같은 값을 가진 후보 중 하나를 고를 때는 쓸모가 있다.

⚠️ P-E5 는 9번 수정으로 성격이 바뀐다. 클래스코드가 아니라 표의 실제 수치가
일치해서 붙으므로, 이 문항의 인용은 **정당한 근거**다.

## 3. 서브답변이 전부 검증 실패해도 아무 데도 안 걸리던 문제 — 이슈 1

`combine_answer` 의 `rescue` 는 "인용 0건 + 검증 통과 → 살리고 고지" 인데, 그 대칭인
"인용 있음 + 전부 검증 실패" 가 비어 있었다. 인용이 1건이라도 있으면 게이트를
통과하고, `blocks` 는 `verified` 와 무관하게 전부 합성에 들어간다.

**빼지 않고 살리되 고지한다.** P-A2 는 서브질문이 하나뿐이라 빼면 빈 답변이 나간다.

- 합성 프롬프트에 "근거 번호 붙은 문장만 사실로 다루고 단정하지 마라" 를 넣고
- 답변 끝에 `config.UNVERIFIED_NOTE` 를 **코드로** 붙인다

프롬프트 지시만으로 두지 않은 이유는 거절문구 건에서 6·7·8차 세 번 다 안 지켜진
전례가 있어서다.

## 4. 값 대조가 원리상 못 잡는 두 유형 — 이슈 1·6(b)

`unsupported_values` 는 문자열로 나타난 값만 본다. P-A2 의 진짜 피해 둘이 여기서 샜다.

**(a) 없는 상품을 만들어 냈다** — `_placeholder_funds()`
"A채권형펀드", "B혼합형펀드" 처럼 변별부가 ASCII 한 글자인 이름만 잡는다.
한글 한 음절("그펀드")은 대명사일 수 있어 제외했고, 코퍼스 펀드명과 겹치면 안 잡는다.

**(b) 위험도를 서술로 뒤집었다** — `_asset_claim_conflicts()`
한 문장 안에서 ① 카드가 있는 펀드가 불리고 ② 카드와 반대되는 단어만 있고
③ 맞는 단어·부정 표현은 없을 때만 잡는다. 형제펀드는 변별자까지 봐야 한다
(자체 점검에서 형제 오탐이 나와 고쳤다).

둘 다 **답변을 고치지 않고 카드 사실을 각주로 덧붙인다.** 판정이 빗나가도 맞는
사실이 한 줄 늘 뿐이라 손해가 없는 비대칭 구조다.

## 9. 단위를 머리에 선언한 표를 값 대조가 못 읽던 문제 — P-E5 재분류

**P-E5 는 환각이 아니었다.** 9차 검토서에 "환각 확정 15개" 로 적힌 값들은
답변이 인용한 p47 청크의 표에 **그대로 있는 값**이다.

```
p47  나. 연도별 수익률 추이(단위:%)
     종류A-e   -23.33   36.13   -30.82   19.20   33.59
답변  종류 A-e  -23.33%  +36.13%  -30.82%  +19.20%  +33.59%
```

값도 순서도 표와 일치한다. `_TOK_HIGH` 의 백분율 패턴이 `%` 기호를 요구하는데
투자설명서 실적표는 기호를 셀마다 붙이지 않고 표 머리에 한 번 선언한다. 그래서
**청크 쪽에서 값이 하나도 추출되지 않았고**, 답변 쪽 토큰만 남아 교집합이 비었다.

> **⚠️ 2026-09-02 수치 정정.** 아래 표의 앞 세 줄은 처음에 412건 / 재무241·요약140 /
> 8,322개 대 423개로 적혀 있었는데 **재현되지 않는다.** 같은 코퍼스에 어떤 정규식을
> 걸어도 412 도 241:140 도 나오지 않는다. 재측정값으로 바꾼다 —
> `python -m scratchpad.audit_counts corpus` 로 그대로 재현된다.

| | 값 |
|---|---:|
| 투자설명서 청크 (section 7,721 + 펀드카드 92 + 클래스카드 91) | 7,904건 |
| 그중 현행 규칙(`_UNIT_PCT`)이 여는 청크 | **263건 (3.3%)** — 재무·운용실적 164 · 요약정보 99 |
| 그 안의 값: `12.34%` 형태 | 148개 |
| 그 안의 값: 맨숫자 `12.34` | **3,951개 (26.7배)** |
| 9차 `unsupported_values` 중 이 경로 오탐 | 35개 중 **16개(46%)** — P-E5 15 · P-E1 1 |

패턴을 바꿔 세면 이렇게 갈린다 — 총계가 어디서 왔는지 남겨 둔다.

| 패턴 | 청크 | 재무·운용실적 | 요약정보 |
|---|---:|---:|---:|
| **현행 코드규칙 `_UNIT_PCT`** | **263** | 164 | 99 |
| 리터럴 `단위:%` | 102 | 92 | 10 |
| 괄호형 `(단위…%)` | 284 | 192 | 91 |
| 같은 줄에 `단위` 와 `%` | 423 | 323 | 99 |

논지는 어느 패턴에서도 그대로다 — 선언형 표 안에서 맨숫자가 `%` 표기를 22~27배로
압도하고, 걸린 청크의 62%가 재무·운용실적에 몰려 있다.

**수정** — `_tokens()` 가 텍스트에 `단위:%` 선언이 있으면 맨숫자도 백분율로 읽는다
(`_UNIT_PCT` · `_BARE_DEC`). 표가 스스로 "이 숫자들은 %다" 라고 밝힌 경우에만 열어서
조항 번호·페이지·배수가 값으로 잡히지 않는다.

**실측 (동일 청크 집합 A/B, 78문항)**

```
unsupported_values          184 → 169   (전부 P-E5 의 15개. 다른 문항 변화 0)
값으로 근거가 확인된 인용    100 → 103   (P-E5 3건이 진짜 근거로 복구)
```

> **⚠️ 2026-09-02 단위 표기 정정.** 위 184·169 는 **서브답변 × 그 서브질문의 청크
> 집합**을 하나씩 replay 하며 센 값이라 중복이 포함돼 있고, 결과 파일의
> `unsupported_values` 필드(**최종 답변 기준, 문항당 1회**)와 단위가 다르다.
> 같은 실행의 필드 합은 **35개 / 7문항**이다. 두 수를 나란히 놓으면 안 된다.
>
> 앞으로는 `python -m scratchpad.audit_counts runs <결과.json>` 이 찍는 세 필드를
> 기준으로 한다 — 셋이 서로 다른 단위이고, 그 사실이 출력에 적혀 나온다.
>
> | 필드 | 뜻 | 9차 | 10차 |
> |---|---|---:|---:|
> | `unsupported_values` | 최종 답변 기준 | 35 / 7문항 | 32 / 14문항 |
> | `unsupported_values_pre` | 재작성 전 서브답변 기준 | 18 / 9문항 | 20 / 15문항 |
> | `unsupported_values_new` | 재작성이 새로 만든 값 | 24 / 5문항 | 14 / 3문항 |

**P-E5 에 남은 5개가 진짜 결함이다** — `2020년`~`2024년`. 답변이 표의
`최근1년차`(24.01.01~24.12.31)를 **2020년으로 라벨링해 연도 축을 뒤집었다.**

```
실제 2024년 종류A = -23.62% (손실)
답변 2024년 종류A = +33.38% (이익)      ← 5년 추이가 정확히 거꾸로
```

지표가 이제 오탐 15개 대신 **진짜 오류 5개**를 가리킨다. 별개로 종류C-e 의 2024년
칸(`2.26%`)은 p47 청크가 잘려 값이 없자 p46 의 **설정이후** 연평균을 끌어다 채운
것으로, 이건 실제 오배치다.

## 서버 쪽 (파이프라인 밖, 참고)

`PENSION_LLM_CONCURRENCY` 는 기본 0(꺼짐) 그대로 뒀다. 429 재현 테스트 해석은
중앙값 60.2→68.1 로 **조금 늘고** 최악값 104.0→69.8 로 줄었다는 쪽이 정확하다
(평균이 줄어 보인 건 무제한 3회차 104초 하나 때문). 서버에서 429 가 나면
`PENSION_LLM_CONCURRENCY=4` 로 켜면 되고, 이제 `retries_429` 로 효과를 셀 수 있다.
