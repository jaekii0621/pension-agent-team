# A. 문제와 수정

## A-1. 🔴 구조화 파싱 실패가 "인용 0건인 정상 답변"으로 둔갑했다

### 무엇이 문제였나

`nodes/answer_generator.py` 의 답변 스키마는 이렇게 생겼다.

```python
class GeneratedAnswer(BaseModel):
    main_answer: str                                           # 필수
    citations: List[CitationRef] = Field(default_factory=list)  # ← 기본값 []
    evidence_sufficient: bool = Field(default=True)             # ← 기본값 True
```

펀드 비교처럼 **표를 요구하는 문항**에서 벌어지는 일을 순서대로 따라가면:

**① 모델이 JSON 대신 마크다운 표를 쓴다.** 중괄호가 하나도 없다.

**② 복구 호출조차 건너뛴다.** `llm/clova_client.py` 에 이런 분기가 있다.

```python
if "{" not in (text or "") and _free_text_field(schema):
    obj = _salvage_text(text, schema)      # 고쳐 달라고 묻지도 않고 구제로 직행
```

원래 의도는 옳다 — "JSON을 시도조차 안 한 응답은 고쳐 달라고 해봐야 출력 토큰만
2배 쓰고 대개 같은 모양을 낸다"는 실측 근거가 주석에 있다.
그런데 `GeneratedAnswer` 가 하필 이 조건에 걸린다. 필수 `str` 필드가
`main_answer` 하나뿐이라 `_free_text_field` 가 "자유 서술형"으로 판정한다.

**③ 여기가 함정이다.** `_salvage_text` 는 원문을 `main_answer` 에 담고
`model_validate` 를 부른다. 나머지 두 필드에 기본값이 있으니:

```
citations           = []      ← 인용을 못 뽑은 게 아니라 '없다'고 기록된다
evidence_sufficient = True    ← 판단한 적이 없는데 '근거 충분'으로 기록된다
```

**Pydantic 검증을 통과한다. 예외도, 에러 로그도 없다.**
파싱 실패가 "인용 0건인 정상 답변"으로 조용히 둔갑한다.

**④ 구제 경로 둘도 같이 무너진다.**

| 경로 | 조건 | 왜 실패하나 |
|---|---|---|
| 복원 | 본문에 `[1]` `[2]` 표기가 있어야 | JSON 형식조차 안 지킨 모델이 인용 표기는 지켰을 리 없다 |
| 값 대조 | 답변의 수치가 청크에 그대로 있어야 | 숫자 없는 서술형 정책 답변은 대조할 값이 없다 |

**⑤ 마지막에 흔적까지 지워진다.** 합성 단계의 `_verify_cites` 는 출처 목록에 없는
`[n]` 을 전부 제거한다. `global_cites` 가 비었으니 **본문의 모든 인용 번호가
삭제되고 출처 섹션도 안 붙는다.**

> **결과**: 유창하고 그럴듯한 답변 + 근거 표시 0건 + `evidence_sufficient = True`.
> 대회 평가가 근거표시·인용정확도를 보는데, 답은 맞고 출처만 없는 상태로 나간다.
> 그리고 시스템 어디에도 "실패했다"는 신호가 남지 않는다.

### 어떻게 고쳤나

**스키마에서 기본값을 빼는 것은 하지 않았다.** `citations` 를 필수로 만들면
`_free_text_field` 가 자유서술형 판정을 안 하게 되고, **구제 경로 자체가 막혀서
파싱 실패한 서브질문이 통째로 죽는다.** 그 실패는 이미 겪었다 —
`clova_client.py` 주석: *"1차 실행: 6건이 이렇게 유실"*.
인용 없는 답변을 답변 없음으로 바꾸는 건 손해다.

**구제는 그대로 두고, 구제였다는 사실만 신호로 남긴다.**

```python
n_salvage_before = len(llm.salvages)
res = llm.structured(system, user, GeneratedAnswer, ...)
salvaged = len(llm.salvages) > n_salvage_before
...
"evidence_sufficient": bool(res.evidence_sufficient) and not salvaged,
"evidence_ok":        bool(res.evidence_sufficient and cites) and not salvaged,
```

`trace` 요약에도 `⚠구제경로(파싱실패)` 가 붙는다.

### ⚠️ 확증이 아니라 가설이다

위 ①~⑤는 **코드 경로상 가장 유력한 설명**이지, 개별 문항이 실제로 이 경로를
탔다는 증거는 아직 없다. 7차 결과 파일(8/25 생성)에는 `salvage` 필드가 없다.

**`eval/run_queryset.py` 는 이미 이 필드를 기록하도록 되어 있다** —
결과 파일이 그 코드보다 오래됐을 뿐이다.
**8차 실행부터 `salvage` 가 자동으로 찍힌다.** 이걸로 가설이 검증된다.

## A-2. 🟠 근거 없는 값이 최종 답변과 무관한 텍스트 기준이었다

### 무엇이 문제였나

`unsupported_values`(환각 후보)는 `generate_answer` 가 **서브답변**을 보고 계산한
값이었다. 그런데 사용자가 실제로 받는 최종 답변은 combiner 가 **다시 쓴 별도
텍스트**다. 즉 결과 파일의 환각 후보 목록이 실제 답변과 무관했다.

실측(7차): P-B3 는 "3등급"이 근거 없는 값으로 기록됐는데 **최종 답변에는 그
문자열이 아예 없다.** 재작성 과정에서 사라진 값을 놓고 환각이라고 판정할 뻔했다.
P-D5 도 같은 형태였다.

곁가지로, 등급 표기가 두 가지("위험등급 2" / "2등급")라 토큰 교집합이 헛돌면서
**근거 있는 등급이 근거 없는 값으로 잡히는** 문제도 있었다(7차 P-A1).

### 어떻게 고쳤나

- combiner 가 **최종 답변을 근거 청크와 다시 대조**해 `unsupported_values` 산출.
  문자열 대조만 하므로 **LLM 호출 0회**
- 서브답변 기준 값은 `unsupported_values_pre` 로 보존
- `unsupported_values_new` = final − pre = **재작성이 새로 만들어낸 값**
- `rag_worker` 가 `documents` 를 넘겨 combiner 가 같은 근거 집합을 보게 함
- `state.py` 에 두 필드 선언 (선언이 없으면 LangGraph 가 버린다)
- 등급 표기를 `N등급` 하나로 정규화

> ⚠️ `_new` 를 곧바로 환각으로 읽지 말 것. 재작성이 표기를 바꾼 것
> ("12.5%" → "12.5퍼센트")도 여기 들어온다. **건수부터 보고 손으로 분류한다.**
> 지금 임계값이나 룰을 만들지 않는다.

## A-3. 🟠 실패하면 문항이 통째로 망가지는 자리가 경량 모델이었다

### 무엇이 문제였나

기존 모델 배정은 "출력이 짧으면 DASH" 라는 이분법이었다. 그런데 **짧은 출력이라고
다 같지 않다.** 틀렸을 때 문항 하나가 통째로 망가지는 자리가 (A) 안에 섞여 있었다.

가장 이상했던 것은 **구조화 출력 복구 호출**이다.

```
HCX-005 가 실패한 JSON  →  DASH-002 에게 "고쳐 달라"고 보낸다
```

여기가 실패하면 `citations` 가 통째로 빈다. 즉 **근거표시 0건**이다.

### 어떻게 고쳤나

새 상수 3개. 전부 환경변수로 되돌릴 수 있다.

| 상수 | 자리 | 호출 빈도 | 올린 이유 |
|---|---|---|---|
| `MODEL_DECOMPOSE` | 질문 분해 · 잔여 재분해 | 질문당 1~2회 | 분해가 어긋나면 아래 전 단계가 엉뚱한 걸 풀고 **뒤에서 복구 불가** |
| `MODEL_SAFETY` | 안전성 범주 판정 | 질문당 1회 | 범주가 출력 문구를 가름. '프롬프트공격' 오분류 = 평가지표 6번 대응 문장 소실 |
| `MODEL_REPAIR` | 구조화 출력 복구 | **실패 시에만** | 실패하면 인용이 통째로 빈다 |

셋 다 호출 수가 적어 지연·레이트리밋 부담이 거의 없다.

`eval` 메타(`_meta.params.models`)에도 기록되므로 A/B 비교가 가능하다.

### `MODEL_GRADE` 는 DASH 로 남겼다

문서 채점은 **질문당 최대 8회를 `GRADE_WORKERS` 만큼 동시에 쏘는 유일한 자리**다.
6차에서 P-B1 을 죽인 429 버스트가 정확히 여기서 났다. 올리려면 동시성을 함께
내려야 하므로, 별도 실험으로 남긴다.

```bash
CLOVA_MODEL_GRADE=HCX-005 PENSION_GRADE_WORKERS=2 python -m eval.run_queryset
```

### ⚠️ 이 상향은 A-1 을 고치지 못한다

A-1 의 주 경로(중괄호 없는 응답)는 **복구 호출을 타지도 않는다.**
`MODEL_REPAIR` 상향은 "JSON을 시도했지만 형식이 깨진" 경우에만 듣는다.

# B. 검토했으나 적용하지 않은 것

자문 5개 항목 + 자체 검토. **하지 않기로 한 판단도 기록으로 남긴다.**

| 제안 | 판정 | 이유 |
|---|---|---|
| 429 백오프에 **Jitter 추가** | ❌ 이미 있음 | `clova_client.py:177` 에 지수 백오프 + jitter + `Retry-After` 우선이 모두 구현돼 있다 |
| 재시도 **6회** / 백오프 **5.0** | ⚠️ **되돌릴 것 권고** | 최악 대기 95초(jitter 포함 133초). 서버 타임아웃 300초에 지연 max 162초를 겹치면 터진다. 재시도는 *복구*지 *예방*이 아니다 — 필요한 건 스레드 공유 토큰버킷 |
| 거절 문구 **정규식 일괄 제거** | ❌ 하면 안 됨 | 범주별로 갈린다. 위법조력·유해는 **넣지 마라**, 프롬프트공격은 **반드시 넣어라**(평가지표 6번). 일괄 제거하면 점수가 깎인다. 옳은 형태는 `safety_category` 조건부 (제거 + **주입**) |
| `citations` **기본값 제거** | ❌ 하면 안 됨 | 구제 경로가 막혀 파싱 실패한 서브질문이 죽는다(전례 6건). A-1 의 신호화로 대체 |
| **4,000자 상한** 상향이 지연 악화 | ❌ 전제가 틀림 | `max_answer` 는 결과 파일 기록용 `truncate()` 일 뿐. 생성을 제한하지 않아 **지연과 무관**. 실제 상한은 `max_tokens`(answer 2000 / combine 2500) |
| 표 **상위 5행만** 렌더 | ⚠️ 순서가 틀림 | 잘린 건 78건 중 1건. P-A3 는 표가 곧 답이라 행을 자르면 정답 펀드가 사라진다. 실제 낭비는 **셀 공백 패딩과 열 구조**다 — 정보 손실 0인 것부터 |
| combiner **Scratchpad 강제** | ❌ 처방이 과함 | 파생 수치는 이미 `calc_result` 에 있다. **화이트리스트로 걸러내면 LLM 호출 0회.** Scratchpad 는 가장 비싼 모델의 가장 느린 노드에서 출력 토큰을 늘려 지연 최적화와 정면충돌하고, CoT 제거용 후처리 위험이 하나 더 생긴다. n=4 에서 기계장치를 만들 단계가 아니다 |
| 문서 0건 시 **원본 그대로 폴백** | ⚠️ 전례 있음 | `give_up` 은 이미 `generate` 로 간다(거절 직행 아님). 진짜 결함은 `grade_documents` 가 `documents` 를 **덮어써서** 채점 전 랭킹이 소실되는 것. 다만 "상위 3건 폴백"은 2026-08-18 에 **틀린 출처를 만들어서 제거된 설계**다. 되살린다면 폴백 문서를 **인용 대상에서 제외**해야 한다 |
| 질의 사전 임베딩 캐시 | ❌ 삭제함 | 로컬 실행용으로 만들었으나 콜랩 실행으로 확정되어 불필요. A-4 개선만 남김 |

### `truncate()` 부수 문제

`utils.py` 의 `truncate()` 는 **개행을 공백으로 치환**한다. 지금 결과 파일의
답변은 표 구조가 이미 뭉개져 있어서, **최적화하려는 그 표를 볼 수 없는 상태**다.
표 토큰 최적화를 하려면 이것부터 고쳐야 한다.

당장은 실행 시 상한을 키워 우회한다.

```bash
python -m eval.run_queryset --max-answer 20000
```

| **A-1** 구제 경로 가시화 | 인용 0건 31건의 원인이 구제 경로인지 **처음으로 판별** | `salvage` 필드에 `answer:*:json_없음` 이 몇 건 찍히는가 | **높음** — 기록은 확정, 건수만 미지 |

| **A-2** 환각 후보 정확도 | 최종 답변에 없는 문자열을 환각으로 오판하지 않음 (7차 P-B3·P-D5 형태) | `unsupported_values` 와 `_pre` 의 차이 | **높음** |

| **A-3** 분해 품질 | 서브질문이 원 질문을 제대로 덮어 하위 단계 낭비 감소 | `sub_questions`, LLM 호출 수 | 중간 |
| **A-3** 안전성 범주 | 프롬프트공격 오분류 감소 → 평가지표 6번 대응 문장 보존 | `blocked`, `safety_reason` | 중간 |

### 지연에 대한 정직한 예상

A-3 상향으로 질문당 2~3회가 경량 모델에서 고성능 모델로 옮겨간다.
**지연은 다소 늘어날 것이다.** 다만:

- 질문당 22회 중 2~3회이고, 채점(최대 8회)은 건드리지 않았다
- 지연 상관 1위는 총토큰(0.78)인데, 이 세 자리는 **출력이 짧다**
- 현재 p90 74.7초 / max 162초. 서버 타임아웃 300초까지 여유가 있다

늘어난 지연이 max 200초를 넘기면 **되돌리거나 `MODEL_DECOMPOSE` 만 남길 것.**

# D. 8차 실행에서 볼 것

우선순위 순.

1. **`salvage` 필드** — A-1 가설의 검증. 인용 0건 31건 중 몇 건이
   `answer:*:json_없음` 인가. 이게 이번 실행의 **가장 중요한 산출물**이다.
2. **인용 0건 수** — 31건에서 움직였는가. (A-3 만으로 크게 줄지는 않을 것으로 본다)
3. **`unsupported_values_new`** — 건수를 세고 **손으로 분류**한다.
   계산 파생 / 표기 변형 / 진짜 환각. 룰은 그다음이다.
4. **지연 p90·max** — 200초를 넘기면 A-3 를 되돌린다.
5. **표 문항 8건의 출력 토큰** — `--max-answer 20000` 으로 실제 표를 확인한 뒤
   셀 패딩 제거를 프롬프트에 넣을지 판단한다.

### 실행 커맨드

```bash
python -m eval.run_queryset --max-answer 20000
```

### 아직 손대지 않은 것 (다음 사이클 후보)

- **`calc_result` 화이트리스트** — 파생 수치를 환각 후보에서 제외. LLM 호출 0회
- **거절 문구 범주 조건부 처리** — 프롬프트공격 문장 **주입**으로 100% 보장

- **클라이언트 토큰버킷** — 429 를 재시도가 아니라 요청률로 막는다
- **`truncate()` 개행 보존**
